# Gemtrack — полное описание проекта

Один документ, в котором есть всё: что за проект, зачем он нужен, как устроен
изнутри, что делает каждый модуль, какие алгоритмы в нём работают и где
известные слабые места. Написан по состоянию кода на 22 августа 2026.

---

## 1. Что это

**Gemtrack («жила»)** — локальная система накрутки счётчика «Games Watched»
на самоцветах наблюдателя (Spectator Gem) в Dota 2 и последующей продажи
выращенных предметов.

Экономика проста. Spectator Gem вставляется в косметический предмет и несёт
счётчик просмотренных матчей. Steam Market не умеет ценообразовать по счётчику:
гем с 2000 просмотров и пустой гем лежат в одном лоте по одной цене. Пустой
гем стоит полцента на сторонней площадке (market.dota2.net), предмет
со счётчиком 2000+ продаётся на Steam Market за несколько долларов.

Разница между этими двумя ценами — весь бизнес проекта.

Счётчик поднимается **одним сообщением игровому координатору (GC)** — ни игры,
ни реплея, ни просмотра не нужно:

```
k_EMsgUpgradeLeagueItem = 7203

message CMsgUpgradeLeagueItem {
    optional uint64 match_id  = 1;
    optional uint32 league_id = 2
}
```

Ответ `7204` + `msg 26` — счётчик поднят. Ответ `7204` без `msg 26` —
«счётчика не будет» (дубль, негодный матч или отвергнутое сообщение —
по протоколу неразличимы). Отсутствие ответа — «не знаем».

### Ключевое свойство, из которого выросла вся архитектура

Одно сообщение поднимает **все подходящие вещи разом**:

```
2000 отправок Empire  →  1 вещь на 2000, если держишь одну
                      →  20 вещей на 2000, если держишь двадцать
                         отправок в обоих случаях 2000
```

Вторая и двадцатая вещь стоят ноль отправок — только цену гема (полцента).
Поэтому система оптимизирует не отправки, а **вещи на выходе**.

Второе свойство — дедупликация на аккаунт, не на предмет: повторная отправка
того же матча тем же аккаунтом возвращает `dup`, а новый гем на том же
аккаунте уже сожжённые матчи не поднимает. Отсюда смысл второго аккаунта:
он жжёт тот же пул матчей с нуля.

### Стек

- **Движок:** Node.js 22+ (нативный `node:sqlite`, `--test`, запуск .ts без
  сборки), Fastify 5. Внешний отправщик — отдельным процессом `node` из `gcwatch`.
- **Фронт:** React 19, Vite 6, Tailwind 4. Связь с сервером — SSE, без опроса.
- **БД:** SQLite (WAL), без ORM.

## 3. Как устроен бэкенд

### 3.1. Общая картина

```
             каждые 20 с (tick)
                    ▼
        ┌──────────────────────────┐
        │  autopilot.tick()        │  по каждому включённому аккаунту
        │  обновляет инвентарь     │
        │  вызывает worker.decide()│
        └───────────┬──────────────┘
                    ▼
   решение: idle | start | restart | rebuild | watch | halt
                    │
      ┌─────────────┼──────────────┬─────────────┐
      ▼             ▼              ▼             ▼
  ждать новых    поднять       пересобрать    следить за темпом
  гемов          отправщик     очередь        (delay.txt на ходу)
                                    │
                                    ▼
                        очередь в autopilot-<id>.csv
                                    │
                                    ▼
                    внешний процесс gcwatch/index.js
                    (сессия token-<id>.json, отправка 7203)
                                    │
                    пишет status-<id>.json (recent/current)
                                    │
                    fs.watch → ingestStatus() → burned/events в SQLite
```

### 3.2. `server/index.ts` — каркас сервера

Fastify на порту 4322. Три контура:

1. **SSE** `/api/stream` — сервер сам толкает состояние (`buildState()`)
   при изменении файлов отправщика, инвентаря или POST-командах.
2. **`fs.watch(GC)`** — следит за `status-*.json` / `delay.txt`,
   разбирает отчёты отправщиков и разносит расход по аккаунтам
   (`ingestStatus()`): в ленту `events` попадает всё, в журнал `burned` —
   только `update` и `dup`, никогда `silent`.
3. **Два таймера**: `tick()` работника (интервал из настроек, проверка срока
   каждые 5 с) и `cycle()` — обновление инвентаря/экипировки + прогрев карты
   матчей по инвентарю (`warmOwned()`).

### 3.3. `server/worker.ts` — чистое решение «что делать дальше»

Единственный модуль без ввода-вывода, проверяется тестами. На вход — снимок
состояния, на выход — действие:

```ts
export type Snapshot = {
  enabled: boolean          // включён ли работник
  senderAlive: boolean      // жив ли процесс отправщика
  queueLength: number       // сколько матчей осталось в очереди
  inventoryChanged: boolean // изменился ли состав гемов
  lastSendAt: number        // последняя отправка, 0 = ещё ни разу
  now: number
  failures: number          // падения подряд
  target: number | null     // сколько отправок заказано; null = до конца
  done: number              // сделано в этом заходе
  senderStartedAt: number   // когда подняли процесс
  displaced: number         // сколько раз выбило другой сессией Steam
  until: number             // до какого времени работать; 0 = без срока
}
export type Action = 'idle' | 'start' | 'restart' | 'rebuild' | 'watch' | 'halt'
```

Порядок проверок существенен и закреплён тестами:

- срок и цель — **раньше пересборки**: иначе гем, купленный в последнюю
  секунду, продлил бы заказанное;
- состав инвентаря — раньше всего живого: жечь по устаревшей очереди
  значит терять только что купленные гемы;
- `displaced >= 2` (аккаунт занят другой сессией) — halt: ждать бессмысленно,
  вход удаётся, выбивают после;
- молчание после успешных отправок — минута; невозможность войти — пять минут
  (у отправщика своя лестница отходов 15/30/60/120 с).

Важная деталь — `freshSendAt()`: метка последней отправки учитывается, только
если её сделал **нынешний** процесс. Файл отчёта переживает перезапуск
компьютера, и вчерашняя метка выглядела как «молчит 22 часа» — работник
убивал живой отправщик каждый такт.

### 3.4. `server/autopilot.ts` — исполнение и состояние работников

Один юнит (`Unit`) на аккаунт, всё в памяти:

```ts
type Unit = {
  enabled, delay, auto        // выключатель, пауза, автоподбор темпа
  target, ordered             // живая цель и что человек просил (1000 → 1147)
  until, even                 // срок работы и растянуть ли работу до срока
  cap, capped                 // потолок счётчика на гем и дошедшие до него
  needSends, needFrom         // расчёт «сколько отправок до потолков»
  waves, plan                 // партии разброса (когда добавлять вещи)
  only: string[] | null       // какие гемы жечь; null — все из инвентаря
  startedAt, startBurned      // от чего считается «сделано»
  queueLength, fingerprint    // длина очереди и отпечаток состава
  failures, log               // падения и журнал решений
  ...
}
```

Ключевые функции:

- `picks()` — что жечь: все гемы в инвентаре, у которых известна сущность
  (`gem-map.json`, kind = team|player). Состав инвентаря и есть выбор.
- `picksFor(u)` — гемы этого аккаунта минус дошедшие до потолка.
- `rebuild(a, u)` — собирает очередь (`queueFor`), пишет csv-файл, удаляет
  старый журнал отправщика, запоминает `needSends` (сколько отправок реально
  уйдёт до потолков — не до конца очереди).
- `made(a, u)` — сделано в заходе по журналу расхода в БД
  (`burnedCount − startBurned`), а не по счётчику в памяти: перезапуск
  панели не обнуляет заказанный прогон.
- тик `tickOne()`: тупик по свежести счётчиков (Steam 429) → halt вслепую
  не работаем; потолки → пересборка; затем `decide()` и исполнение действия,
  включая подбор паузы на ходу через `delay.txt`.

Слепой потолок опаснее отсутствующего: он обещает остановку, которой не будет,
а матчи тратятся необратимо — поэтому при устаревших счётчиках работник
останавливается сам.

### 3.5. `server/sender.ts` — управление процессами отправщика

Отправщик — внешний `gcwatch/index.js`, один процесс на аккаунт, свои файлы
очереди/статуса/сессии (`autopilot-<id>.csv`, `status-<id>.json`,
`token-<id>.json`). Панель его спавнит и убивает.

- `isAlive()` проверяет и `exitCode`, и `signalCode`: убитый сигналом процесс
  оставляет код пустым навсегда, и панель 20 минут считала мёртвого живым.
- Пауза передаётся **только файлом** `delay.txt`, без флага: флаг у отправщика
  главнее файла, и прогон намертво вставал на стартовом темпе. Через файл темп
  читается перед каждой отправкой и меняется на ходу.
- Отчёт прошлого запуска стирается при старте — иначе метки со вчерашнего дня
  выглядели как сегодняшние.
- При падении панели все отправщики гасятся (`process.on('exit') → stopAll`),
  осиротевших процессов не остаётся.

### 3.6. `server/queue.ts` — сборка очереди матчей

Две вещи, ради которых модуль существует:

**Слияние.** Матч, входящий в наборы двух сущностей (Empire и BZZ делят 209
матчей), отправляется один раз и засчитывается обеим. Без слияния половина
времени тратится впустую.

**Порядок.** Внутри сущности — от полезных к дешёвым: сначала поднимающие
двоих, потом нетронутые, в самом конце — уже отвечавшие пусто (`tried`).
Спорные не выкидываются: отвергнутый матч неотличим от дубля и может быть
живым. Между сущностями — круговая раздача (`rotate()`): один круг — по одному
матчу каждой, чтобы старые команды (матчи по номеру = по времени) не забрали
весь прогон себе.

Матч без `league_id` в очередь не попадает вовсе: GC молча отвергает такое
сообщение (проверено 20 августа на матче 8003261364).

`burnedSet` вычитает только `state = 'confirmed'`; `triedSet` (`state = 'dup'`)
матчи не запрещает, а понижает в хвост.

`sendsNeeded(rows, need)` — не оценка, а **проигрывание всей работы наперёд**:
круг за кругом, с выбыванием гемов, дошедших до потолка, и обрезкой долга
по запасу. Без учёта выбывания счёт выходил 11 154 вместо честных 8 367.
Это число — знаменатель растяжки по времени.

### 3.7. `server/spread.ts` — разброс счётчиков и потолки

Двадцать девять предметов BZZ идут в ногу и приходят к одному числу —
на витрине это выглядит тем, чем является. Отсюда:

- `livelyTarget(base, seed)` — «живое» число: заказ плюс 0,3–34 %,
  не оканчивающееся на круглое. 1000 → 1147. Дешёвый детерминированный хеш:
  перезапуск панели не меняет план.
- `spreadPlan(base, waves, seed)` — партии с разными моментами добавления:
  счётчик вещи равен числу отправок после её появления, поэтому вещи,
  добавленные по ходу, получают разные числа. Партии разносятся ровным шагом
  (полоса 18 % от заказа) с дрожанием 2,5 %, совпадения и круглые хвосты
  разводятся. Работник сам говорит, когда добавлять следующую партию
  (`nextWave`).
- `capFor(goal, gem)` — потолок на гем: довести каждую вещь примерно до
  заданного числа, а не выжигать весь запас команды. Выжженный запас означает,
  что гем той же команды, купленный завтра, не поднимется вовсе.

### 3.8. `server/pace.ts` — подбор паузы и растяжка по сроку

Пауза — единственная ручка, меняющая выход. Замер 20 августа: 76 отправок
в минуту при паузе в секунду, отклик GC 340 мс по медиане.

- `advise(samples)`: пока GC отвечает на каждую отправку, темп можно поднимать
  (шаг ×0,8); появились молчания — потолок, отходим (×1,4, при доле молчаний
  > 10 % — ×2). Дубли не считаются: они говорят про матч, а не про скорость.
- `creditRate(update, dup)` — доля отправок, за которые действительно
  начислили. Без неё прогон при половине пустых отставал бы вдвое.
- `evenDelay(msLeft, sendsLeft, floor)` — «до десяти утра» как «раздели работу
  на срок», а не «жги как можешь и встань в десять». Пересчитывается каждый
  тик, промахи выправляются сами.
- `silenceLimit(base, delay)` — предел молчания привязан к паузе: на растяжке
  пауза бывает больше минуты, постоянный предел убивал бы живого отправщика.

### 3.9. `server/steam.ts` — инвентарь и экипировка

Все запросы к Steam идут через одну очередь с зазором 2,5 с — иначе 429
и отказ на часы. На 429 — бэкофф 5 минут. User-Agent браузерный: с «rig»
Steam под нагрузкой уходил в 429 на часы, с обычным именем отвечал 200.

Парсинг описаний предмета даёт `gem` (имя гема), `hero` (Used By), `value`
(Games Watched), набор (`setPieces`), и `carrier` — голый самоцвет
(`Spectator: X`, без героя) или предмет с вставленным. Это разный товар
и разная цена.

Снимок счётчиков пишется в БД только при изменении — история для графика.

### 3.10. `server/accounts.ts` — аккаунты

Реестр `accounts.json` (метка, steamid, файл сессии), сессия — файл
`token-<id>.json` в `gcwatch`, ключ от аккаунта никуда не копируется.
Первый аккаунт заводится сам из существующего `token.json`.

Привязка нового — QR-кодом: панель не логинится сама, вход умеет отправщик
(`--dry --save-token`), панель слушает его вывод (`QRURL`, `STEAMID`).
Тот же steamid дважды не заводится. При отвязке журнал расхода остаётся:
матчи на том аккаунте действительно израсходованы.

### 3.11. `server/ledger.ts` + `db.ts` + `migrate.ts` — журнал расхода

Арбитр всегда GC, локально мы только помним:

| state | откуда | верим ли |
|---|---|---|
| `confirmed` | пришёл msg 26 | да, израсходован |
| `dup` | 7204 без msg 26 | «счётчика не будет», причина неизвестна |
| `silent` | GC не ответил | **не пишется вовсе** |

`silent` раньше писался — и один зависший ответ навсегда исключал матч
из будущих списков.

Таблицы SQLite:

- `burned (account, match_id, …, state)` — журнал расхода, PK `(account, match_id)`.
  Развязан по аккаунтам миграцией `splitByAccount`: до этого `match_id` был
  общим PK, и второй аккаунт унаследовал бы пустую очередь.
- `events (ts, …, account)` — лента всех отправок, включая silent.
- `counters (ts, gem, assetid, item, value)` — история счётчиков для графиков;
  `counterLines()` сливает одинаковые ветки («BZZ ×70» вместо 70 кривых).
- `supply`, `entity_matches` — старая оценка запаса и кэш матчей сущностей.
- `vmatch`, `vplayer` — карта матчей (обходчик, см. терминальные утилиты).

Запись в журнал — единственная точка `ingestOne()`, и только для `update`/`dup`.

### 3.12. `server/market.ts` + `purchase.ts` — закупка

Площадка market.dota2.net: гемы по полцента против трёх-четырёх на Steam,
лотов сотни. Список цен открытый, ключ нужен только для покупки.

- `rank()` — сначала доходящие до цели (`pool >= goal`), внутри дешевле
  и объёмнее; `per1000` — цена за тысячу счётчиков.
- `plan()` — брать вширь: вторая копия уже накручиваемого гема стоит ноль
  отправок, но и новая команда даёт свой запас.
- Закупка — наблюдаемая работа (`purchase.ts`): каждый лот в журнал сразу,
  остановить можно в любой момент, до трёх заходов по списку. Перед каждым
  лотом спрашивается нынешняя цена: дешёвые кончаются по мере скупки.
  Выросла выше допуска — позиция пропускается.
- Цена передаётся потолком (`buyOne`): площадка возьмёт самый дешёвый лот
  не дороже неё. Множители мелкой единицы различны (рубль — сотня,
  доллар — тысяча): перепутать значит переплатить вдесятеро.
- Гривны у площадки нет — пересчёт доллара по курсу НБУ, в панели подписано,
  где точная цена, а где пересчёт.

Вторая точка входа к трате денег отсутствует намеренно.

### 3.13. Прочее

- `state.ts` — сборка полного состояния для SSE: мои гемы (каждая вещь
  отдельно), каталог с `per1000`, «жила» (самая представительная сущность),
  темп, последнее подтверждение. Кэши на 10 с.
- `api.ts` — граф пересечений (рёбра — общие матчи, «что покупать вместе
  выгодно»), превью очереди, дерево «гем → турниры», список израсходованных,
  пул наборов (сколько полных комплектов собирается, чего не хватает).
- `graph.ts` — пары через обратный индекс матч → сущности.
- `valve.ts` — Steam Web API как первоисточник матчей (OpenDota и STRATZ —
  зеркала, каждое теряет куски; засчитывает гем Valve по своим записям).
- `opendota.ts` — добор матчей сущности с кэшем в SQLite; для игрока —
  только лобби первого типа.
- `settings.ts` — все пороги в файле, с пределами: панель — не место, где
  можно случайно выставить паузу в ноль. Каждая отправка необратима.
- Терминальные утилиты `rig/*.ts` — `crawl` (обход Valve по лигам,
  `GetMatchHistory` со курсором `start_at_match_id`), `merge-mirrors`
  (слияние источников), `remeasure`, `supply-report`, `plan-burn`,
  `plan-purchase`, `status`.

## 5. Фронтенд

**Экраны** (`dash/src/views/`):

- **Work (Пульт)** — главный: тумблер работника (не «пуск», работа либо идёт,
  либо нет), очередь/до конца/темп/последнее подтверждение, товар по каждому
  гему (счётчик против потолка, прогресс-бар), что делать работнику
  (журнал решений), настройки прогона (цель, срок, потолок, партии, выбор
  гемов), состояние отправщика с логом.
- **Accounts** — инвентарь и счётчики по каждому аккаунту, состояние сессии,
  QR-привязка нового, переименование/отвязка.
- **Buy (Закупка)** — что докупить и почему: доходящие до цели, цена
  за тысячу счётчиков, «взять всё дешевле…», план с суммой, ход закупки
  лотом за лотом с возможностью остановить.
- **Graph** — сущности узлами, рёбра — общие матчи; видно, что покупать
  вместе выгодно.
- **Review (Журнал)** — история отправок с турнирами и тем, чьим гемам
  матч поднял счётчик.

**Части** (`dash/src/parts/`): `Chart` (график счётчиков волнами,
сворачиваемые списки), `Tune` (настройки с пределами), `Launcher`
(вкл/выкл работника), `LinkAccount` (QR), `Modal`, `Reveal`, `Sidebar`, `ui`.

**Связь** (`lib/api.ts`): одна SSE-подписка (`useLive`), ничего не опрашивается;
`useJson` для второстепенных экранов с зависимостью от тика потока; `post`
с полной блокировкой в демо-режиме — за кнопкой «запустить» необратимые
сообщения GC. Демо-режим (`VITE_DEMO=1`) — обезличенный снимок в сборке,
внешних запросов нет.

## 6. Потоки данных за один тик работника

```
tick (каждые ~20 c, по каждому включённому юниту)
  1. refreshInventory()            Steam, очередь 2,5 с, бэкофф на 429
  2. счётчики устарели?            да → halt «потолок вслепую не считаю»
  3. cappedGems() изменился?        да → пересборка даже при том же составе
  4. decide(snapshot)              чистое решение из worker.ts
  5. исполнение:
     rebuild → queueFor → csv → стоп отправщика (следующий тик поднимет)
     start   → spawn gcwatch/index.js (delay только файлом)
     watch   → подбор паузы: even ? evenDelay(срок, отправки/creditRate)
                                    : advise(замеры)
     halt    → выключить юнит, остановить отправщика, причина в журнал
```

Расход замыкается через файлы: отправщик пишет `status-<id>.json`,
`fs.watch` → `ingestStatus()` → `burned`/`events` в SQLite → следующая
пересборка очереди уже вычитает подтверждённое. Панель перезапущена —
отправщик пишет дальше, при старте панели `ingestStatus()` догоняет журнал.

## 7. Известные проблемы (аудит 22.08.2026)

Логика, которая сейчас сломана или врёт:

1. **Многоаккаунтность не реализована на уровне данных.** Инвентарь читается
   только для первого аккаунта (`STEAMID` в `steam.ts`), все юниты делят один
   `inv`; `delay.txt` один на всех отправщиков; `state.ts` для `current`
   читает захардкоженный `status.json`. Второй аккаунт будет жечь гемы
   первого и считать потолки по чужим счётчикам.
2. **Защита от краш-лупа не работает.** `failures` растёт только при ошибке
   спавна и сбрасывается при любом успешном запуске процесса — падающий
   по кругу отправщик не останавливается никогда.
3. **`sendsNeeded` проигрывает работу в другом порядке** (`order()` вместо
   `rotate()`), чем реальная очередь, — ETA систематически расходится.
4. **Граф ломается на многословных именах**: ключ ребра `a + ' ' + b`,
   разбор `split(' ')` — «Evil Geniuses» + «Team Liquid» даёт узлы «Evil»
   и «Geniuses».
5. **Инвентарь обрезается на 2000 вещей** (`count=2000`, без пагинации).
6. Мелочи: `events` с PK `ts` (коллизии миллисекунд), `/api/build` выкидывает
   `dup` вопреки философии журнала, `spent` в закупке считается по потолку
   цены, а не по факту, ETA без учёта доли пустых отправок, `capFor` даёт
   до +34 % к цели, юниты не переживают перезапуск панели, сервер слушает
   `0.0.0.0` без ключа (для локального проекта достаточно `127.0.0.1`).

Тесты: 243, все проходят (`rig && npm test`) — но они покрывают чистые
модули (`worker`, `queue`, `spread`, `pace`, `ledger`, `purchase`), а не
интеграцию юнитов с общими `inv`/`delay`.

## 9. Чем этот проект отличается

- **Необратимость как первый класс.** Каждая отправка тратит матч навсегда;
  поэтому всё опасное за явными действиями, молчание GC не пишется в расход,
  потолки вслепую не работают, у настроек пределы.
- **Комментарии как журнал решений.** Почти каждый неочевидный кусок кода
  ссылается на дату и замер, из-за которого он такой («панель 20 минут считала
  мёртвого живым», «очередь начиналась с восьмисот спорных»).
- **Чистое ядро, проверяемое тестами.** Решение работника, очередь, разброс,
  темп, журнал — функции без ввода-вывода; сервер только исполняет их решения.
