# Этап 2.4: экран «Аккаунты» — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** вместо заглушки «Аккаунты» в `?ui=v2` — рабочий экран по §5.5 и макету `5-akkaunty.html`: карточки аккаунтов с проверками, «второй аккаунт», настройки выбранного аккаунта, общие правила, справа — работник и его решения; окна привязки по QR и отвязки. **Две сессии Steam показываются раздельно** и никогда не сводятся в одно «жива / отозвана».

**Как устроено:** чистые функции (слова и тон каждой проверки, четыре цифры карточки, подсказки «если что-то сломалось») — модулем `v2/accounts/model.ts`; экран и правая колонка — компоненты v2. Сервер меняется **только** там, где без него нельзя показать веб-сессию (решения 1–2); логика работника, отправщика и привязки игровой сессии не меняется.

**Стек:** React 19, Node 24, `node:test`. Без новых зависимостей. Проверка экрана — только в показе (`VITE_DEMO=1`); живой `rig` для вёрстки не запускается, накрутка не включается.

**Спецификация:** §3 (правила), §4.3 (клавиатура), §5.5 (Аккаунты), §5.7 («Накрутить» через подтверждение), §6 (данные), §12.4 (вход). Макет: `…/2026-10-03-gemtrack-redesign/5-akkaunty.html`. Дорожная карта: этап 2.4. Инвариант от рецензента (2026-10-04): «экран должен показывать две разные сессии, а не снова сводить их в один ok/revoked: игровая SteamClient — unknown + срок токена; вебовая WebBrowser — отдельное фактическое состояние веб-сессии».

**Порядок работы:** сверка по этапу целиком: план → одобрение → все задачи → один PR → CI и рецензия → мёрдж по «мёрдж #N». Живые действия — только по отдельному «да» владельца.

## Решения, которые нужно сверить до кода

1. **Две сессии — два поля, два слова, две кнопки** (инвариант рецензента).
   - **Игровая (SteamClient, `token.json` / `token-<id>.json`)** — `sessionState` в `/api/accounts` считается **при каждом запросе из файла** (`sessionFromToken`, без сети, как `checkSession`), а не берётся из кеша: так срок токена виден сразу, без нажатия. Состояния: `unknown` + `validUntil` («вход игры: токен до 12.03.2027 · жив ли — видно только клиенту»), `revoked` (срок истёк — «истёк DD.MM, нужен QR»), `missing`, `error`. Слова «жива» у игровой сессии **нет**: проверить её снаружи нельзя (`UNVERIFIABLE`). Кнопка «перечитать» — тот же `session-check`. Признак, что Steam действительно отверг вход, приходит только от отправщика (`fatal` «отправщик не смог войти») — показывается строкой работника, не статусом сессии.
   - **Веб (WebBrowser, `token-web-<id>.json`)** — новое поле `web` в `/api/accounts`: `{ state: 'missing' | 'expired' | 'unchecked' | 'ok' | 'error', validUntil, checkedAt, error }`. Без сети: `missing` — файла нет; `expired` — `exp` токена прошёл; `unchecked` — файл есть, с запуска сервера не проверялся. С сетью — только по кнопке: **новый маршрут `POST /api/accounts/web-check {id}`** → `checkWeb(a)` (один обмен токена на куки через `webcookies.js`, тот же путь, что импорт истории 3.3); итог кешируется в памяти сервера → `ok` («веб-вход работает, проверено N мин назад») или `error` (текст ошибки). Имена кук в ответ **не** отдаются (сейчас `checkWeb` их возвращает — маршрут отдаёт только состояние).
   - Тип `AccountRow` в `lib/api.ts`: `sessionState.validUntil?` и `web?` — только добавлением.
   - *Отступление от §5.5:* там «одна строка „Сессия Steam“» и «все маршруты уже есть». Спецификация писалась до разделения сессий (3.3); строк проверок становится четыре: вход игры, веб-вход, ключ площадки, инвентарь.

2. **Веб-вход по QR в панели.** Предлагаю **вариант Б**:
   - **А (минимум):** веб-входа в панели нет; при `missing` / `expired` / `error` карточка пишет «нужен веб-вход: `node tools/gcwatch/weblogin.js --id <id>`» (команда без секретов). Сервер — только решение 1.
   - **Б (рекомендую):** маршруты `POST /api/accounts/web-link {id}` и `/web-link/cancel` по образцу `linkStart`: сервер запускает `weblogin.js --id <id> --out token-web-<id>.tmp.json`, отдаёт `QRURL` в `link`-состоянии (то же окно с QR), по `STEAMID` **сверяет с steamid аккаунта**: совпал — временный файл переименовывается в `token-web-<id>.json`, кеш кук аккаунта сбрасывается (`forgetWeb`); не совпал — временный файл удаляется, ошибка «вошли другим Steam (…)». Игровой токен и работник **не трогаются** (веб-вход не выбивает игру — `weblogin.js:12`). В `weblogin.js` — новый ключ `--out` (имя файла внутри `gcwatch`, проверка как у `--id`); без `--out` поведение прежнее.
   Почему Б: сейчас `weblogin.js` пишет токен сразу в итоговый файл — отсканированный не тем телефоном QR молча подменит веб-вход аккаунта; в прошлый раз QR пришлось рисовать в PNG вручную. Одновременно идёт только одна привязка (игровая или веб) — общий признак «привязка уже идёт».

3. **Карточка аккаунта** (§5.5): аватар с лампой (лампа — `unit.running`), имя + ✎ (`rename`), steamid, «привязан DD.MM.YYYY»; четыре цифры: **сожжено** (`burned`), **в очереди** (`queueLength`), **пауза** (`delay` мс / «сама» при `auto` / «к сроку» при `even`), **гемов X из Y** (X — `only.length` или Y при `only = null`; Y — гемы инвентаря этого аккаунта, как считает `picksFor`; если в данных Y нет — «все из инвентаря», без числа). Четыре строки проверок (решение 1 + ключ + инвентарь) — цвет и слово:
   | строка | состояния → слово | кнопки |
   |---|---|---|
   | вход игры | `unknown`+срок → «токен до …, жив ли — видно клиенту»; `revoked` → «истёк …»; `missing` → «нет»; `error` → «не читается: …» | «перечитать», «обновить по QR» |
   | веб-вход | `ok` → «работает · проверено N назад»; `unchecked` → «не проверен»; `expired` → «истёк …»; `missing` → «нет»; `error` → «не работает: …» | «проверить», «войти по QR» (решение 2) |
   | ключ market.dota2.net | `missing` → «не задан»; `unchecked` → «не проверен»; `ok` → «проверен N назад»; `mismatch` → «чужой Steam (…)»; `invalid` → «площадка отвергла: …» | «вставить ключ» / «заменить», «проверить», «удалить» |
   | инвентарь | `private` → «закрыт»; `error` → «ошибка: …»; иначе «открыт · N вещей · снимок N назад»; `truncated` → «не весь (обрезан)»; нет `inv` → «ещё не читался» | — |
   Низ: «▶ Накрутить» (существующий `ConfirmBurn`), подсказка `unit.why`, «отвязать».

4. **Карточка «Второй аккаунт»** (пунктир): «вход по QR, пароль не нужен; второй аккаунт крутит те же матчи заново» → существующее окно `LinkAccount` (игровая привязка).

5. **Настройки выбранного аккаунта и общие правила** — через существующие `POST /api/autopilot` и `POST /api/settings`, новых полей нет:
   - пауза: чипы «сама · 0,5 · 1 · 2 · 5 · 30 с» (`auto` / `delay`), чипы ниже `settings.pace.floor` неактивны с подсказкой «ниже пола из общих правил»;
   - цель в отправках (`target`) с пересчётом во время по текущей паузе — метка `оценка`;
   - разброс счётчиков: «нет · 2 · 3 · 4 · 5 партий» (`waves`);
   - гемы чипами с иконками (`only`); гем без карты — пунктиром и неактивен (как в старом `Tune`);
   - общие правила: цель счётчика (`goal`), частота проверки инвентаря (`invTtl`), пол паузы (`pace.floor`) — запись по кнопке «сохранить», границы — те, что проверяет сервер (`settings.ts:94–99`); ошибка сервера — словами рядом.
   Изменения применяются сразу (так на сервере); подписи «действуют только на этот аккаунт» / «на все аккаунты сразу» — как в макете.

6. **Демо.** В снимке один аккаунт без `sessionState`, `market`, `web`. Предлагаю `dash/src/demo/accounts.json` — **составлен руками** (`"_note"`), в точной форме `/api/accounts`: два аккаунта, у которых вместе встречаются все состояния четырёх строк (через переключатель показа нельзя — поэтому второй аккаунт и временная подмена файла на время проверки). Читает его только v2-Аккаунты при `DEMO`; старая панель и `canned()` его не видят — как `buy.json`.

7. **Правая колонка «Работник»** выбранного аккаунта: процесс (`running`, `pid`), падений подряд, выбило сессией (`displaced`), в очереди, последнее решение (`action` + `why`), журнал решений (`log[]`, новые сверху, время `ago`). Блок «если что-то сломалось» показывается только когда есть повод: `fatal` → его текст и «обновить по QR»; `displaced ≥ 2` → «закройте игру и клиент Steam, тогда продолжу» (`worker.ts`); веб-вход `error` / `expired` → «история рынка и продажи не читаются, пока нет веб-входа».

8. **Окна.** Привязка и обновление игровой сессии — существующий `LinkAccount` (без правок). Веб-вход (решение 2Б) — новое окно v2 на тех же QR и шагах, заголовок «Веб-вход „<имя>“ · только чтение сайта Steam». Отвязка — новое окно v2: ввод имени аккаунта для подтверждения, текст из макета (сколько сожжённых матчей останется в журнале); закрывается только кнопками (необратимо — как `ConfirmBurn`). Ключ площадки — небольшое окно с полем `type=password`; после записи сервер сам проверяет ключ (`setKey`), окно показывает итоговый статус, ключ не отображается.

9. **Отвязка удаляет и веб-токен.** Сейчас `unlink` (`accounts.ts:221`) удаляет только игровой токен — `token-web-<id>.json` остаётся на диске без хозяина (а с тем же id после повторной привязки другого Steam его подхватил бы импорт истории). Исправление — в задаче 1, при любом варианте решения 2.

10. **Чего нет:** веб-сессии в старой панели; проверок по таймеру; новых настроек; удаления веб-токена отдельно от отвязки; переноса панели на Railway.

## Отступления при выполнении

1. **Общие правила: «как часто проверять инвентарь» — это `tick`, а не `invTtl`.** В решении 5 ошибка плана: `tick` — «как часто работник смотрит инвентарь» (`settings.ts:17`), `invTtl` — через сколько прочитанный снимок считается устаревшим. Старая панель правит тоже `tick`. Границы — те же, что проверяет сервер.
2. **«▶ Накрутить» — только у активного аккаунта.** Подтверждение `ConfirmBurn` (§5.7) считает строки и включает работника **активного** аккаунта (`state.autopilot`). Чтобы кнопка в чужой карточке не запустила другой аккаунт, у неактивного вместо неё — «сделать активным» (`POST /api/accounts/active`, уже есть) с подсказкой; включённого работника любого аккаунта можно остановить из его карточки (`POST /api/sender/stop {id}`).
3. **Файлы:** окна — одним `v2/accounts/dialogs.tsx` (веб-вход, ключ, отвязка), а не тремя; откуда данные (показ / сервер) — `v2/accounts/data.ts`, чтобы `Accounts.tsx` экспортировал только компоненты (иначе Vite не может горячо перезагрузить модуль).
4. **Тестам — свой реестр аккаунтов.** `tools/accounts.json` рабочий и читается при импорте `accounts.ts`; тест, который привяжет или отвяжет аккаунт, поменял бы список живой панели. `testenv.ts` задаёт `ACCOUNTS_FILE` во временной папке (как `GC_DIR`).
5. **Старая панель** кода не меняла, но данные теперь точнее: игровая сессия в `/api/accounts` считается из файла, поэтому истёкший токен она покажет «отозвана» сразу, без нажатия «проверить».
6. **Выжившая мутация и её закрытие (задача 2):** «при несовпадении steamid временный файл не удаляется» сначала не ловилась — общий обработчик ошибки тоже удаляет временный файл. Добавлен прямой тест `acceptWebToken`; теперь мутация ловится.
