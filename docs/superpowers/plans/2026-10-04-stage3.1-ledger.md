# Этап 3.1: журнал операций + С2 (покупки на площадке) — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** на сервере появляется журнал денежных операций (§16) — одна таблица, записи не меняются, ошибки исправляются сторно. Первая конкретизация — **С2**: покупки гемов и возвраты на market.dota2.net попадают в журнал из **истории площадки** (`operation-history`) и сверяются с нашим журналом закупки.

**Как устроено:** три слоя, у каждого одна роль:
1. **журнал закупки** (`market_buys`) — что МЫ отправили и что ответила площадка в момент покупки (`custom_id`, `id` предмета, цена). Не источник денег;
2. **журнал операций** (`money_ops`) — деньги. Пишется **только** из истории площадки (§15/§17: «история площадки — источник истины») и сторно;
3. **сверка** — какие наши покупки есть в истории, каких нет, какие операции истории пришли не от нас.

`job.log` (`purchase.ts`) остаётся оперативным состоянием и источником денег не становится.

**Стек:** Node 24 (`.ts` напрямую), `node:sqlite`, `node:test`. Без новых зависимостей. Панель не меняется (экран Продаж — этап 2.6).

**Спецификация:** §7 С2, §14 (инварианты 2, 4, 9, 10), §15, §16, §17. Дорожная карта: этап 3.1 («тест: дубль внешней операции не вставляется; правка — только сторно; `job.log` не источник денег»).

## Global Constraints

- **Сервер: сначала тест, потом код** (правило дорожной карты). `cd rig && npm test` — все тесты зелёные; `npm run check`.
- Живой `rig` не запускается. Обращение к площадке — только через `call()` в `market.ts` (общий ограничитель, ключ в заголовке, §14 п. 10). Ключ не попадает в журнал, `raw_ref`, ошибки и логи (§14 п. 4).
- Деньги — **целыми в мелких единицах площадки** (RUB — копейки, ×100; USD/EUR — тысячные, ×1000; `VERIFIED`, docs-v2, 2026-10-04) и с валютой. Никаких float для сумм.
- **Финансовые поля записи журнала операций неизменяемы, запись не удаляется. Единственное допустимое изменение — однократная отметка `reconciled_at: NULL → время`; любые другие `UPDATE` и любые `DELETE` запрещены.** Это обеспечивает сама база (триггеры), а не дисциплина кода.
- `source` и `external_id` — `NOT NULL`: в SQLite `UNIQUE` пропускает несколько строк с `NULL`, и без этого дубль внешней операции прошёл бы мимо уникальности (§14 п. 2).
- Старое поведение закупки не меняется: `purchase.ts` — только добавление записи в журнал закупки.

## Решения, которые нужно сверить до кода

1. **Имена.** `rig/server/ledger.ts` уже занят журналом сожжённых матчей. Новое: `rig/server/money.ts` (журнал операций), `rig/server/markethistory.ts` (разбор истории и импорт), таблицы `money_ops`, `market_buys`.
2. **Деньги пишет только история площадки.** Наша покупка в момент `buy` пишется в журнал закупки, **не** в журнал операций. Иначе одна покупка попала бы в деньги дважды (из ответа `buy` и из истории), а совпадает ли `id` с `item_id`, не описано. Так §14 п. 2 держится при любом ответе на эту гипотезу.
3. **Внешний номер: в схеме — только `UNIQUE(source, external_id)`.** Как строится `external_id` для истории площадки — чистая функция `externalId(row)` в `markethistory.ts`, которую можно заменить после задачи 2 **без миграции схемы**. **После живого чтения:** есть `custom_id` → `buy:cid:<custom_id>`; нет → `buy:item:<item_id>:<time>`. В выборке за 180 дней `item_id` и `custom_id` не повторяются, у завершённых строк `time` не менялся; время в номере — защита от повторной покупки того же лота. Сторно — `storno:<id исходной>`: это наш номер, от площадки не зависит.
4. **Какие события пишутся** (после живого чтения). В журнал операций — **только `buy` со `stage = 2` для предметов `Spectator: …`** → «покупка гема». Всё остальное — **`skipped` с причиной**, деньги не трогает:
   - `buy` со `stage = 5` — «сделка отменена (`causer` / `cancellation_reason`), возврат денег по API не подтверждён» (**вариант (а)**, решение сверки 2026-10-04) и строкой в отчёте сверки;
   - `buy` со `stage = 1` или без `stage` — «не завершена»: её подберёт следующий импорт, запись не придётся менять;
   - `buy` не-самоцвета — «не самоцвет»;
   - `refund` — «событий возврата вживую не видели, форма не проверена»;
   - `sell`, `checkin`, `checkout` — «нет денежного типа в §16»;
   - строка с непонятными полями — «не разобрано».
   Это не «деньги игнорируются навсегда»: типы и события можно добавить, когда их форма будет наблюдена.
5. **Суммы.** Хранятся целыми в мелких единицах площадки и с валютой. `gross` — сумма по модулю, `net` — изменение денег владельца со знаком (расход `−`, приход `+`, сторно — `−net` исходной). **Сумма покупки — поле `paid`** (строка с целым в мелких единицах; вживую `paid` истории = `paid` проверки по `custom_id` × 100 для RUB): `gross = paid`, `net = −paid`. Тест — на обезличенной строке той же формы. Валюты кроме RUB — по docs-v2 (×1000), вживую не видели. `fee_steam`/`fee_game` для площадки — `null`.
6. **`status`** — nullable. Пишется только `stage = 2` → `передан` (решение 4), сам `stage` всегда лежит в `raw_ref`. Незавершённые (`stage = 1`) не пишутся, поэтому смена `stage` после записи не возникает — запись не меняется.
7. **`reconciled_at`** — при импорте `NULL`. Ставится, только когда сверка действительно нашла соответствие нашей покупке (`market_buys`). Неизменность при этом сохраняется точно: триггер `BEFORE UPDATE` пропускает **единственное** изменение — `reconciled_at` из `NULL` в значение, один раз, при неизменных остальных полях; любое другое `UPDATE` и любое `DELETE` → `RAISE(ABORT)`.
8. **`user_id`** — пока одна учётка: константа `owner` (пользователи — этап 7). `account_id` — id рабочего аккаунта (`main`, …), чей ключ читал историю.
9. **Сторно** — `storno(db, id, reason, by)` в одной транзакции: новая запись `type = сторно`, `net = −net` исходной, ссылка на исходную в `raw_ref`, `created_by` и причина обязательны (§14 п. 9). Ошибка внутри — откат целиком, ничего не вставлено; повторное сторно той же записи — отказ без частичной записи.
10. **`raw_ref`** — строка истории площадки как JSON (ключа в ответе нет; проверяется тестом).
11. **Импорт — по запросу, окнами. Окна — наше ограничение, не факт площадки.** `POST /api/money/sync {id, since?}`: от `since` (по умолчанию 30 дней назад) до сейчас **режем запрос на окна не длиннее 7 суток** — защита от неописанных пределов и постраничности; тест проверяет именно нарезку, а не «площадка поддерживает 7 дней». В ответе — окна, строки, вставлено / уже было / пропущено с причинами. По таймеру не запускается.
12. **Журнал закупки `market_buys` — не денежная запись.** Пишется в `purchase.ts` при «куплено» (обычном и подтверждённом по `custom_id`): `custom_id`, `item_id` (из `buy` или `get-buy-info-by-custom-id`), `hash_name`, цена в мелких единицах, валюта, аккаунт, время — это «цена и факт покупки» §15. **Инвариант:** `market_buys` не ссылается на `money_ops` и не участвует в суммах; связь появляется только как результат сверки (`reconciled_at` у операции). Только добавление — ход закупки не меняется; неудачные попытки сюда не пишутся.
13. **Сверка** — `GET /api/money/reconcile?id=`: (а) наши покупки без операции истории («нет в истории площадки»), (б) операции истории без нашей покупки («куплено не через Gemtrack»), (в) отменённые покупки (`stage = 5`) — «отменена: `causer` / `cancellation_reason`; возврат денег по API не подтверждён (со слов владельца — возвращаются)»; (г) **сколько отмен по вине покупателя** (`buyer_cancelled`) за период — с предупреждением: со слов владельца, частые отмены покупателем дают статус нежелательного покупателя и временную блокировку. Найденные соответствия ставят `reconciled_at`; больше ничего не правится.
14. **Чего нет в 3.1:** экрана (Продажи — 2.6), продаж на рынке Steam (3.3), ключей TF2 (3.4), выплат Clover (3.2), автозапуска импорта, пересчёта валют.

### Task 4: журнал закупки, отмены и сверка

Три слоя, три факта (решение сверки 2026-10-04):
`money_ops` — только доказанное движение денег; `market_buys` — что купил Gemtrack; `market_cancellations` — что площадка сказала об отмене.

**`market_buys`** (что купил Gemtrack; не деньги, на `money_ops` не ссылается):

```
id, account_id NOT NULL, custom_id NOT NULL, hash_name NOT NULL,
ask_price NOT NULL (целое, мелкие единицы), currency NOT NULL,
buy_id (id из ответа buy — «ID предмета»; связь с item_id истории не проверена),
item_id (из get-buy-info-by-custom-id, если покупку подтверждали по custom_id),
bought_at NOT NULL, how NOT NULL ('buy' | 'custom_id'),
UNIQUE(account_id, custom_id)
```

- **`ask_price` — цена, отправленная в `buy`**, а не списанная сумма. `buyOne()` передаёт её потолком: площадка берёт самый дешёвый лот не дороже (`market.ts`), фактическая сумма может быть ниже. Единицы — те же, что ушли в запрос: `units(цена, валюта)` из `market.ts`, целое в мелких единицах. Фактическую сумму `market_buys` не хранит — её правда в `money_ops` (`paid` истории). Поведение закупки не меняется.
- **`item_id`** — только у `how = custom_id`: `judgeBuyInfo()`/`resolveAmbiguous()` в `purchase.ts` получают в результат `itemId` из ответа `get-buy-info-by-custom-id` (добавление поля; `paid` в этом ответе — в основных единицах, поэтому здесь не используется).
- **Запись через колбэк**, а не базу в закупке: `startPurchase(..., { onBought })` — закупка отвечает за факт «куплено», хранение — `marketbuys.ts`; `index.ts` передаёт `recordBuy(db, …)`. Ошибка колбэка закупку не останавливает: записывается в лог и в ответ сверки нет — строка просто отсутствует (сверка покажет покупку как «до журнала закупки» или «нет в журнале»).
- Пишется при «куплено»: обычном (`how = buy`) и подтверждённом по `custom_id` после неясного ответа (`how = custom_id`). Отказы и «неясно» не пишутся.
- Сверка сопоставляет **только по `custom_id`** — `buy_id` хранится как есть, но ни с чем не сравнивается: совпадает ли он с `item_id` истории, вживую не проверяли.
- Только вставка: `UPDATE`/`DELETE` запрещены триггерами.

**`JOURNAL_START`** — момент включения журнала закупки **в этой базе**, а не константа в коде: при первом создании таблиц `marketbuys.ts` один раз записывает время в служебную строку (`market_meta`, ключ `journal_start`, вставка без замены), дальше оно только читается. Так граница точна для каждой базы (живая, копия, тест) и не требует ставить дату руками при выкладке. Правка/удаление строки запрещены триггером.

**`market_cancellations`** (что площадка сказала об отмене; не деньги):

```
id, account_id NOT NULL,
cancel_key NOT NULL  -- 'cid:<custom_id>' или, без custom_id, 'item:<item_id>:<happened_at>'
custom_id, item_id NOT NULL, happened_at NOT NULL,
causer, cancellation_reason,         -- из get-buy-info-by-custom-id
checked_at,                          -- когда спросили; NULL — спросить нельзя (нет custom_id)
raw_ref,                             -- ответ проверки как JSON (ключа в нём нет — тест)
UNIQUE(account_id, cancel_key)
```

- **`raw_ref`:** у проверенной отмены — JSON ответа `buyInfo()`; у отмены без `custom_id` — JSON исходной строки `operation-history` (основание статуса «площадку спросить нельзя»).
- Успешный ответ проверки без `causer`/`cancellation_reason` — строка всё равно пишется как проверенная (`checked_at` стоит), в отчёте — «причина неизвестна».
- Один уникальный ключ `cancel_key` вместо пары колонок: в SQLite `UNIQUE` пропускает `NULL`, а у отмены без `custom_id` его нет. Естественный ключ — `custom_id`; запасной — `item_id + happened_at`, как просила сверка.
- **Только вставка, без правок:** строка пишется один раз — уже с ответом проверки. Если площадка не ответила, строка **не пишется**, отмена попадает в «не проверено» в ответе сверки и спрашивается при следующем запуске. Отмена без `custom_id` (купили не через Gemtrack) пишется сразу с `checked_at = NULL` и причиной «нет custom_id — площадку не спросить».
- `UPDATE`/`DELETE` запрещены триггерами.

**Сверка** — `reconcileCancellations()` и `reconcile()`:

1. Вход — `cancelled` из `syncHistory()` (покупки со `stage = 5`). **Сначала дедупликация по `account_id + cancel_key`** — одна отмена может прийти из соседних окон или дважды за запуск; одна отмена → не больше одного внешнего запроса за запуск, и лимит 20 считается уже по уникальным. Для каждой: есть строка в `market_cancellations` → площадку не трогаем; нет и есть `custom_id` → **один** `get-buy-info-by-custom-id` через общий ограничитель (`buyInfo()`), записать ответ. Не больше 20 новых проверок за запуск — остальные со следующим (защита от всплеска запросов).
2. **Причину не вычисляем из `stage = 5`** — только из ответа проверки (`causer`, `cancellation_reason`).
3. Ни в одном случае отмена не попадает в `money_ops`.
4. `reconcile(db, accountId)` — отчёт, без правок, кроме `reconciled_at`:
   - (а) наша покупка (`market_buys`) без операции истории (`money_ops` `buy:cid:<custom_id>`) и без отмены → «нет в истории площадки»;
   - (б) операция истории без нашей покупки:
     - `custom_id` вида `gt-…` и `happened_at < JOURNAL_START` → «покупка Gemtrack до журнала закупки» (правило проекта: такой `custom_id` формирует наш робот; это наблюдавшийся формат, а не доказательство по архиву, что других источников `gt-…` нет);
     - `custom_id` вида `gt-…` и `happened_at ≥ JOURNAL_START` → **«покупка Gemtrack отсутствует в журнале»** — так видна, например, упавшая запись `onBought`, а не прячется под историческую;
     - без `custom_id` или чужой → «куплено не через Gemtrack»;
   - (в) отмены из `market_cancellations`: `seller_cancelled` — обычная отмена; `buyer_cancelled` — отмена покупателем; без проверки — «причина неизвестна»; у всех — «возврат денег по API не подтверждён»;
   - (г) **риск**: число `buyer_cancelled` за последние 30 дней — с пометкой «со слов владельца: частые отмены покупателем дают статус нежелательного покупателя и временную блокировку»;
   - совпадение (а)↔операция по `custom_id`, **та же валюта и фактическая сумма не выше потолка запроса** (`money_ops.gross ≤ market_buys.ask_price`) → `markReconciled()`. Списано меньше потолка — нормально (лот был дешевле), в отчёте счётчик «дешевле запроса». Списано **больше** потолка или валюта другая → «сумма расходится», `reconciled_at` не ставится.

### Предложения на сверку (до задачи 3)

1. **Сумма покупки** — `paid` (целое, мелкие единицы): `gross = paid`, `net = −paid`. Валюты кроме RUB — по docs-v2, с пометкой, пока не увидим вживую.
2. **`externalId()`**: есть `custom_id` → `buy:cid:<custom_id>`; нет → `buy:item:<item_id>:<time>` (время — защита от повторной покупки того же лота; у этих полей изменений не видели).
3. **`status`**: `stage` 2 → `передан`, 5 → `просрочен`. Строки со `stage = 1` (или без `stage`) **не пишутся** — «не завершена», их подберёт следующий импорт: так запись не придётся менять, когда сделка закончится.
4. **Просроченная покупка — открытый вопрос, сужен.** Проверено вживую двумя запросами `get-buy-info-by-custom-id` по двум нашим покупкам со `stage = 5` (согласовано, только чтение):
   - **блока `refund` нет ни у одной**; `paid` ×100 = `paid` истории (обе);
   - есть поля, которых нет в истории: `causer` и `cancellation_reason` — у одной `seller` / `seller_cancelled`, у другой `buyer` / `buyer_cancelled`; также `send_until`, `receive_until`, `trade_id`, `bot_id`;
   - **признака «деньги возвращены» в ответе нет** — ни суммы, ни номера возврата. Ни история, ни проверка по `custom_id` не подтверждают возврат; что деньги вернулись на баланс площадки — известно только `со слов` владельца (ниже), в API этого не видно.

   Варианты на решение владельца и сверки:
   - (а) **не писать просроченную покупку в деньги**: `skipped` «сделка отменена (`causer`/`cancellation_reason`), возврат денег по API не подтверждён», и строкой в отчёте сверки — чтобы её видел человек. Если деньги вернулись — итог верен; если нет — «вложено» занижено;
   - (б) писать покупку `−paid` и выведенный возврат `+paid` с пометкой «выведено из stage 5»: итог тот же, что в (а), но выдаёт непроверенное за запись;
   - (в) писать только покупку `−paid` со статусом «отменена»: если деньги вернулись — «вложено» завышено.

   **Решение сверки (2026-10-04): вариант (а).**

   **Со слов владельца** (метка `со слов`, §3.3; не наблюдение по этим двум покупкам): при `seller_cancelled` деньги возвращаются; при `buyer_cancelled` — тоже возвращаются, но **частые отмены покупателем дают статус нежелательного покупателя и временную блокировку**. На странице сделки на сайте отменённая покупка помечена «Покупка (X) Не удалась» с той же суммой со знаком минус; отдельное начисление возврата там не видно. Поэтому возврат остаётся вне журнала денег (вариант (а)), а число отмен покупателем — в отчёте сверки как риск для закупки.

5. **Ошибки окна** — импорт повторяет окно с ошибкой (до 2 раз, через ограничитель), а неудачные окна перечисляет в ответе; вставленное из других окон остаётся. Запрос «на весь период разом» импорт не делает.
6. **`checkin`** — `skipped` «нет денежного типа в §16 (похоже на пополнение баланса)».
