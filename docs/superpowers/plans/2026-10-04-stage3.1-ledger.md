# Этап 3.1: журнал операций + С2 (покупки на площадке) — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** на сервере появляется журнал денежных операций (§16) — одна таблица, записи не меняются, ошибки исправляются сторно. Первая конкретизация — **С2**: покупки гемов и возвраты на market.dota2.net попадают в журнал из **истории площадки** (`operation-history`) и сверяются с нашим журналом закупки.

**Как устроено:** три слоя, у каждого одна роль:
1. **журнал закупки** (`market_buys`) — что МЫ отправили и что ответила площадка в момент покупки (`custom_id`, `id` предмета, цена). Не источник денег;
2. **журнал операций** (`money_ops`) — деньги. Пишется **только** из истории площадки (§15/§17: «история площадки — источник истины») и сторно;
3. **сверка** — какие наши покупки есть в истории, каких нет, какие операции истории пришли не от нас.

`job.log` (`purchase.ts`) остаётся оперативным состоянием и источником денег не становится.

**Стек:** Node 24 (`.ts` напрямую), `node:sqlite`, `node:test`. Без новых зависимостей. Панель не меняется (экран Продаж — этап 2.6).

**Спецификация:** §7 С2, §14 (инварианты 2, 4, 9, 10), §15, §16, §17. Дорожная карта: этап 3.1 («тест: дубль внешней операции не вставляется; правка — только сторно; `job.log` не источник денег»).

## Global Constraints

- **Сервер: сначала тест, потом код** (правило дорожной карты). `cd rig && npm test` — все тесты зелёные (сейчас 378); `npm run check`.
- Живой `rig` не запускается. Обращение к площадке — только через `call()` в `market.ts` (общий ограничитель, ключ в заголовке, §14 п. 10). Ключ не попадает в журнал, `raw_ref`, ошибки и логи (§14 п. 4).
- Деньги — **целыми в мелких единицах площадки** (RUB — копейки, ×100; USD/EUR — тысячные, ×1000; `VERIFIED`, docs-v2, 2026-10-04) и с валютой. Никаких float для сумм.
- **Финансовые поля записи журнала операций неизменяемы, запись не удаляется. Единственное допустимое изменение — однократная отметка `reconciled_at: NULL → время`; любые другие `UPDATE` и любые `DELETE` запрещены.** Это обеспечивает сама база (триггеры), а не дисциплина кода.
- `source` и `external_id` — `NOT NULL`: в SQLite `UNIQUE` пропускает несколько строк с `NULL`, и без этого дубль внешней операции прошёл бы мимо уникальности (§14 п. 2).
- Старое поведение закупки не меняется: `purchase.ts` — только добавление записи в журнал закупки.

## Что известно о площадке (docs-v2, проверено 2026-10-04)

| Факт | Статус |
|---|---|
| `GET /api/v2/operation-history?date=<unix>&date_end=<unix>` → `data[]`: `time`, `settlement`, `causer`, `event`, `item_id`, `market_hash_name`, `price`, `received`, `currency`, `stage`, `custom_id`, `app` | `VERIFIED` (пример ответа в документации) |
| `event`: `buy`, `sell`, `checkout`, `checkin`, `refund` | `VERIFIED` |
| `stage`: 1 — новый, 2 — предмет передан, 5 — трейд просрочен | `VERIFIED` |
| `price`/`received` — целые в мелких единицах валюты | `VERIFIED` |
| `buy` → `{success, id}`, `id` — «ID предмета» | `VERIFIED` |
| `custom_id` уникален у площадки (ошибка «this custom_id exist») | `VERIFIED` (пример ошибки) |
| **поправка к §7 С2:** блок `refund` (`seller`/`market`) описан у `get-buy-info-by-custom-id`, а не у `operation-history`; в `operation-history` возврат — отдельное событие `event = refund` | `VERIFIED` |
| совпадает ли `id` из `buy` с `item_id` в истории | **не описано** → `HYPOTHESIS` |
| у `event = buy` что в `price`, что в `received` | **не описано** → `HYPOTHESIS` |
| сумма возврата у `event = refund` — `price` или `received` | **не описано** → `HYPOTHESIS` |
| меняется ли `time`/`stage` у записи со временем | **не описано** → `HYPOTHESIS` |
| максимальный период, порядок, постраничность `operation-history` | **не описано** |

Всё `HYPOTHESIS` проверяется **живым чтением истории вместе с владельцем (задача 2)** — до того, как смысл сумм попадёт в код. До этого код опирается только на `VERIFIED`; где смысл не подтверждён — строка не идёт в деньги, а попадает в «пропущено» с причиной.

## Решения, которые нужно сверить до кода

1. **Имена.** `rig/server/ledger.ts` уже занят журналом сожжённых матчей. Новое: `rig/server/money.ts` (журнал операций), `rig/server/markethistory.ts` (разбор истории и импорт), таблицы `money_ops`, `market_buys`.
2. **Деньги пишет только история площадки.** Наша покупка в момент `buy` пишется в журнал закупки, **не** в журнал операций. Иначе одна покупка попала бы в деньги дважды (из ответа `buy` и из истории), а совпадает ли `id` с `item_id`, не описано. Так §14 п. 2 держится при любом ответе на эту гипотезу.
3. **Внешний номер: в схеме — только `UNIQUE(source, external_id)`.** Как строится `external_id` для истории площадки — чистая функция `externalId(row)` в `markethistory.ts`, которую можно заменить после задачи 2 **без миграции схемы**. Кандидат до проверки (`HYPOTHESIS`): `<event>:cid:<custom_id>` при `custom_id`, иначе `<event>:item:<item_id>:<time>`; окончательный вид — по наблюдениям задачи 2 (связь `id` ↔ `item_id`, устойчивость `time`). Сторно — `storno:<id исходной>`: это наш номер, от площадки не зависит.
4. **Какие события пишутся.** В журнал операций попадают только события, у которых в §16 есть денежный тип **и** подтверждён смысл суммы (задача 2): кандидаты — `buy` → «покупка гема», `refund` → «возврат за покупку», для предметов `Spectator: …`. Всё остальное (`sell`, `checkin`, `checkout`, не-самоцветы, `buy`/`refund` до подтверждения) — **`skipped` с причиной**: «нет денежного типа в §16», «не самоцвет», «смысл суммы не проверен», «не разобрано». Это не «деньги игнорируются навсегда» — типы можно расширить позже.
5. **Суммы.** Хранятся целыми в мелких единицах площадки и с валютой. `gross` — сумма по модулю, `net` — изменение денег владельца со знаком (расход `−`, приход `+`, сторно — `−net` исходной). **Из какого поля брать сумму** (`price` или `received`) у `buy` и у `refund` — не решаем до задачи 2: разбор поддерживает оба варианта, выбор фиксируется по живому ответу и закрепляется тестом на сырой строке. `fee_steam`/`fee_game` для площадки — `null`.
6. **`status`** — nullable. Значение — нормализованное состояние источника, если оно однозначно; связь со `stage` площадки (`1/2/5`) — `HYPOTHESIS` до задачи 2. Сам `stage` всегда лежит в `raw_ref`. Запись потом не меняется: если `stage` у операции меняется без нового события, это видно в задаче 2 и решается там (отдельной записью или отказом от поля), а не правкой строки.
7. **`reconciled_at`** — при импорте `NULL`. Ставится, только когда сверка действительно нашла соответствие нашей покупке (`market_buys`). Неизменность при этом сохраняется точно: триггер `BEFORE UPDATE` пропускает **единственное** изменение — `reconciled_at` из `NULL` в значение, один раз, при неизменных остальных полях; любое другое `UPDATE` и любое `DELETE` → `RAISE(ABORT)`.
8. **`user_id`** — пока одна учётка: константа `owner` (пользователи — этап 7). `account_id` — id рабочего аккаунта (`main`, …), чей ключ читал историю.
9. **Сторно** — `storno(db, id, reason, by)` в одной транзакции: новая запись `type = сторно`, `net = −net` исходной, ссылка на исходную в `raw_ref`, `created_by` и причина обязательны (§14 п. 9). Ошибка внутри — откат целиком, ничего не вставлено; повторное сторно той же записи — отказ без частичной записи.
10. **`raw_ref`** — строка истории площадки как JSON (ключа в ответе нет; проверяется тестом).
11. **Импорт — по запросу, окнами. Окна — наше ограничение, не факт площадки.** `POST /api/money/sync {id, since?}`: от `since` (по умолчанию 30 дней назад) до сейчас **режем запрос на окна не длиннее 7 суток** — защита от неописанных пределов и постраничности; тест проверяет именно нарезку, а не «площадка поддерживает 7 дней». В ответе — окна, строки, вставлено / уже было / пропущено с причинами. По таймеру не запускается.
12. **Журнал закупки `market_buys` — не денежная запись.** Пишется в `purchase.ts` при «куплено» (обычном и подтверждённом по `custom_id`): `custom_id`, `item_id` (из `buy` или `get-buy-info-by-custom-id`), `hash_name`, цена в мелких единицах, валюта, аккаунт, время — это «цена и факт покупки» §15. **Инвариант:** `market_buys` не ссылается на `money_ops` и не участвует в суммах; связь появляется только как результат сверки (`reconciled_at` у операции). Только добавление — ход закупки не меняется; неудачные попытки сюда не пишутся.
13. **Сверка** — `GET /api/money/reconcile?id=`: (а) наши покупки без операции истории («нет в истории площадки»), (б) операции истории без нашей покупки («куплено не через Gemtrack»), (в) покупка со `stage = 5` без события `refund` («просрочено, возврата не видно»). Найденные соответствия ставят `reconciled_at`; больше ничего не правится.
14. **Чего нет в 3.1:** экрана (Продажи — 2.6), продаж на рынке Steam (3.3), ключей TF2 (3.4), выплат Clover (3.2), автозапуска импорта, пересчёта валют.

### Предложения на сверку (до задачи 3)

1. **Сумма покупки** — `paid` (целое, мелкие единицы): `gross = paid`, `net = −paid`. Валюты кроме RUB — по docs-v2, с пометкой, пока не увидим вживую.
2. **`externalId()`**: есть `custom_id` → `buy:cid:<custom_id>`; нет → `buy:item:<item_id>:<time>` (время — защита от повторной покупки того же лота; у этих полей изменений не видели).
3. **`status`**: `stage` 2 → `передан`, 5 → `просрочен`. Строки со `stage = 1` (или без `stage`) **не пишутся** — «не завершена», их подберёт следующий импорт: так запись не придётся менять, когда сделка закончится.
4. **Просроченная покупка — открытый вопрос, сужен.** Проверено вживую двумя запросами `get-buy-info-by-custom-id` по двум нашим покупкам со `stage = 5` (согласовано, только чтение):
   - **блока `refund` нет ни у одной**; `paid` ×100 = `paid` истории (обе);
   - есть поля, которых нет в истории: `causer` и `cancellation_reason` — у одной `seller` / `seller_cancelled`, у другой `buyer` / `buyer_cancelled`; также `send_until`, `receive_until`, `trade_id`, `bot_id`;
   - **признака «деньги возвращены» в ответе нет** — ни суммы, ни номера возврата. Ни история, ни проверка по `custom_id` не подтверждают возврат; вернулись ли деньги на баланс площадки — `HYPOTHESIS` (по правилам площадки отменённая сделка возвращает деньги покупателю — в API это не видно).

   Варианты на решение владельца и сверки:
   - (а) **не писать просроченную покупку в деньги**: `skipped` «сделка отменена (`causer`/`cancellation_reason`), возврат денег по API не подтверждён», и строкой в отчёте сверки — чтобы её видел человек. Если деньги вернулись — итог верен; если нет — «вложено» занижено;
   - (б) писать покупку `−paid` и выведенный возврат `+paid` с пометкой «выведено из stage 5»: итог тот же, что в (а), но выдаёт непроверенное за запись;
   - (в) писать только покупку `−paid` со статусом «отменена»: если деньги вернулись — «вложено» завышено.

   Предлагаю (а) и одну ручную проверку владельцем: в истории баланса на сайте площадки посмотреть, вернулась ли сумма по одной из этих двух отменённых покупок. Если вернулась — (а) подтверждается наблюдением.

5. **Ошибки окна** — импорт повторяет окно с ошибкой (до 2 раз, через ограничитель), а неудачные окна перечисляет в ответе; вставленное из других окон остаётся. Запрос «на весь период разом» импорт не делает.
6. **`checkin`** — `skipped` «нет денежного типа в §16 (похоже на пополнение баланса)».

## Не входит

Экран денег, продажи Steam, ключи TF2, выплаты Clover, курсы валют, автоимпорт по таймеру, пользователи.
