# Этап 3.1: журнал операций + С2 (покупки на площадке) — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** на сервере появляется журнал денежных операций (§16) — одна таблица, записи не меняются, ошибки исправляются сторно. Первая конкретизация — **С2**: покупки гемов и возвраты на market.dota2.net попадают в журнал из **истории площадки** (`operation-history`) и сверяются с нашим журналом закупки.

**Как устроено:** три слоя, у каждого одна роль:
1. **журнал закупки** (`market_buys`) — что МЫ отправили и что ответила площадка в момент покупки (`custom_id`, `id` предмета, цена). Не источник денег;
2. **журнал операций** (`money_ops`) — деньги. Пишется **только** из истории площадки (§15/§17: «история площадки — источник истины») и сторно;
3. **сверка** — какие наши покупки есть в истории, каких нет, какие операции истории пришли не от нас.

`job.log` (`purchase.ts`) остаётся оперативным состоянием и источником денег не становится.

**Стек:** Node 24 (`.ts` напрямую), `node:sqlite`, `node:test`. Без новых зависимостей. Панель не меняется (экран Продаж — этап 2.6).

**Спецификация:** §7 С2, §14 (инварианты 2, 4, 9, 10), §15, §16, §17. Дорожная карта: этап 3.1 («тест: дубль внешней операции не вставляется; правка — только сторно; `job.log` не источник денег»).

## Global Constraints

- **Сервер: сначала тест, потом код** (правило дорожной карты). `cd rig && npm test` — все тесты зелёные (сейчас 378); `npm run check`.
- Живой `rig` не запускается. Обращение к площадке — только через `call()` в `market.ts` (общий ограничитель, ключ в заголовке, §14 п. 10). Ключ не попадает в журнал, `raw_ref`, ошибки и логи (§14 п. 4).
- Деньги — **целыми в мелких единицах площадки** (RUB — копейки, ×100; USD/EUR — тысячные, ×1000; `VERIFIED`, docs-v2, 2026-10-04) и с валютой. Никаких float для сумм.
- Записи журнала операций не меняются и не удаляются — это обеспечивает сама база (триггеры), а не дисциплина кода.
- Старое поведение закупки не меняется: `purchase.ts` — только добавление записи в журнал закупки.

## Что известно о площадке (docs-v2, проверено 2026-10-04)

| Факт | Статус |
|---|---|
| `GET /api/v2/operation-history?date=<unix>&date_end=<unix>` → `data[]`: `time`, `settlement`, `causer`, `event`, `item_id`, `market_hash_name`, `price`, `received`, `currency`, `stage`, `custom_id`, `app` | `VERIFIED` (пример ответа в документации) |
| `event`: `buy`, `sell`, `checkout`, `checkin`, `refund` | `VERIFIED` |
| `stage`: 1 — новый, 2 — предмет передан, 5 — трейд просрочен | `VERIFIED` |
| `price`/`received` — целые в мелких единицах валюты | `VERIFIED` |
| `buy` → `{success, id}`, `id` — «ID предмета» | `VERIFIED` |
| `custom_id` уникален у площадки (ошибка «this custom_id exist») | `VERIFIED` (пример ошибки) |
| **поправка к §7 С2:** блок `refund` (`seller`/`market`) описан у `get-buy-info-by-custom-id`, а не у `operation-history`; в `operation-history` возврат — отдельное событие `event = refund` | `VERIFIED` |
| совпадает ли `id` из `buy` с `item_id` в истории | **не описано** → `HYPOTHESIS` |
| у `event = buy` что в `price`, что в `received` | **не описано** → `HYPOTHESIS`: `price` — уплачено |
| сумма возврата у `event = refund` — `price` или `received` | **не описано** → `HYPOTHESIS` |
| меняется ли `time` записи при смене `stage` | **не описано** → `HYPOTHESIS`: не меняется |
| максимальный период, порядок, постраничность `operation-history` | **не описано** |

Всё `HYPOTHESIS` проверяется в задаче 5 одним чтением истории на живом ключе **вместе с владельцем**. До этого код опирается только на `VERIFIED` и на устойчивые к ошибке решения ниже.

## Решения, которые нужно сверить до кода

1. **Имена.** `rig/server/ledger.ts` уже занят журналом сожжённых матчей. Новое: `rig/server/money.ts` (журнал операций), `rig/server/markethistory.ts` (разбор истории и импорт), таблицы `money_ops`, `market_buys`.
2. **Деньги пишет только история площадки.** Наша покупка в момент `buy` пишется в журнал закупки, **не** в журнал операций. Иначе одна покупка попала бы в деньги дважды (из ответа `buy` и из истории) — а совпадает ли `id` с `item_id`, не описано. Так инвариант §14 п. 2 держится при любом ответе на эту гипотезу.
3. **Внешний номер (`external_id`, уникален в паре с `source`):**
   - есть `custom_id` → `<event>:cid:<custom_id>` — площадка сама не даёт повторить `custom_id`, а мы шлём его в каждой покупке;
   - нет `custom_id` (купили вручную на сайте) → `<event>:item:<item_id>:<time>`;
   - сторно → `storno:<id исходной записи>` — второе сторно той же записи не вставится.
   Время в номере — защита от повторной покупки того же `item_id` (лот вернули после просрочки и купили снова): без времени вторая настоящая покупка потерялась бы как «дубль». Цена ошибки обратная — если `time` меняется со `stage`, будет лишняя запись; это проверяется в задаче 5 (два чтения с промежутком).
4. **Какие события пишутся:** `buy` → «покупка гема», `refund` → «возврат за покупку» — только для предметов `Spectator: …` (самоцветы). `sell`, `checkin`, `checkout` и покупки не-самоцветов **не пишутся** — в §16 для них нет типа; импорт возвращает их счётчик («пропущено N: …»), молча не теряет.
5. **Знак и поля сумм.** `gross` — сумма операции по модулю (мелкие единицы), `net` — изменение денег владельца со знаком: покупка `−price`, возврат `+сумма`, сторно — минус `net` исходной. `fee_steam`/`fee_game` для площадки — `null` (комиссии Steam тут ни при чём). `status` — `stage` площадки на момент записи как есть; запись потом не меняется: смена `stage` на 5 приходит отдельным событием `refund`.
6. **`reconciled_at` и неизменность.** В §16 у записи есть `reconciled_at`, но записи не меняются. Записи из истории площадки сверены по определению — `reconciled_at = recorded_at` при вставке. Отметка «сверено» для других источников (рынок Steam — этап 3.3) — отдельной таблицей, а не правкой строки. Здесь её нет.
7. **`user_id`** — пока одна учётка: константа `owner` (пользователи — этап 7). `account_id` — id рабочего аккаунта (`main`, …), чей ключ читал историю.
8. **Сторно** — `storno(db, id, reason, by)`: новая запись `type = сторно`, `net = −net` исходной, ссылка на исходную в `raw_ref`, `created_by` и причина обязательны (§14 п. 9). Удаления и правки нет: триггеры `BEFORE UPDATE` / `BEFORE DELETE` на `money_ops` → `RAISE(ABORT)`.
9. **`raw_ref`** — строка истории площадки как JSON (без ключа: в ответе его нет; проверяется тестом).
10. **Импорт — по запросу и окнами.** `POST /api/money/sync {id, since?}` читает историю аккаунта окнами по 7 суток от `since` (по умолчанию — 30 дней назад) до сейчас, по одному запросу на окно через `call()`. Сколько окон и строк, сколько вставлено / уже было / пропущено — в ответе. Само по таймеру не запускается (решим после задачи 5, когда станут известны пределы). Окно в 7 суток — защита от неописанной постраничности; если окно вернёт подозрительно круглое число строк, ответ это помечает.
11. **Журнал закупки** (`market_buys`) пишется в `purchase.ts` при «куплено» (обычном и подтверждённом по `custom_id`): `custom_id`, `item_id` (из `buy` или `get-buy-info-by-custom-id`), `hash_name`, цена в мелких единицах, валюта, аккаунт, время. Только добавление — ход закупки не меняется. Неудачные попытки сюда не пишутся (их и так видно в ленте).
12. **Сверка** — `GET /api/money/reconcile?id=`: (а) наши покупки без операции истории («нет в истории площадки»), (б) операции истории без нашей покупки («куплено не через Gemtrack»), (в) покупка со `stage = 5` без события `refund` («просрочено, возврата не видно»). Только отчёт, без правок.
13. **Чего нет в 3.1:** экрана (Продажи — 2.6), продаж на рынке Steam (3.3), ключей TF2 (3.4), выплат Clover (3.2), автозапуска импорта, пересчёта валют.
