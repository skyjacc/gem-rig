# Этап 3.2: выплаты Clover в журнал операций (С7) — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** владелец вносит выплату Clover.tf руками на экране «Продажи»; она ложится в общий журнал `money_ops`, считается в итог «реализовано» ровно один раз, ошибочная исправляется сторно из интерфейса — с подтверждением и причиной.

**Как устроено:** сервер — два маршрута поверх готовых `addOp` и `storno` (`rig/server/money.ts`) и модуль разбора формы `rig/server/payouts.ts`; панель — форма, список выплат и окно сторно в правой колонке «Продаж», итог «реализовано» и пятый узел пути денег — из журнала чистыми функциями `v2/sales/model.ts`. **Новой таблицы нет** (решение 1).

**Стек:** Node 24 (`node:sqlite`), Fastify; React 19 без новых зависимостей. Проверка вида — только в показе (`VITE_DEMO=1`).

**Спецификация:** §5.4 (Продажи), §7 С7, §16 (определения, журнал операций), §17 (сверка выплат — вручную). Макет: `…/2026-10-03-gemtrack-redesign/4-prodazhi.html` (форма «внести выплату», строки 229–234, 426–427). Дорожная карта: этап 3.2, ветка `feat/clover-payouts`.

**Рамки владельца (2026-10-05) — обязательны для всего плана:**
1. Только выплаты **Clover.tf**. Остальные площадки — будущие этапы.
2. Выплаты — в общем журнале `money_ops`. Второй независимый журнал не создаём; отдельная таблица — только с обоснованием (решение 1: не нужна).
3. Сторно — из интерфейса, с подтверждением и причиной. Исходная запись сохраняется, повторное сторно исключено.
4. Уникальность номера транзакции — **в пределах площадки**, а не признака «вручную». Повтор запроса не создаёт вторую выплату.
5. Выплата не увеличивает «реализовано» повторно, если соответствующая продажа уже учтена: **продажа и получение выплаты — разные события** (решение 2).

**Порядок работы:** план → сверка рецензентом → одобрение владельца → все задачи (сервер — сначала тесты, проверка мутациями) → один PR → CI и рецензия → мёрдж по «мёрдж #N». ## Global Constraints

- Деньги — целые в мелких единицах источника; для выплат Clover — **центы USD** (решение 4). Дробей в базе нет.
- `money_ops` не меняется и не удаляется (триггеры этапа 3.1); исправление — только сторно (`storno()`), одно на запись.
- Суммы разных валют не складываются никогда (§3.3, план 2.6 решение 2).
- В репозиторий — никаких настоящих сумм, номеров транзакций и id: тесты и показ — на выдуманных.
- Маршруты записи — за общим входом и проверкой источника запроса (`auth.ts`, `gate`); в показе `post()` ничего не отправляет.
- §4.3: окна — через `useTrap` (фокус внутрь, Tab извне, возврат фокуса); смысл не только цветом.

## Решения — сверить до кода

**1. Отдельная таблица не нужна.** Всё, что нужно выплате, в `money_ops` есть: `type = 'выплата Clover'`, `source = 'Clover.tf'`, `external_id` — номер транзакции, `happened_at` — когда пришло, `currency = 'USD'`, `net` — сколько пришло (центы), `created_by`, `raw_ref` — подробности ввода (ниже). Неизменяемость, запрет удаления и сторно уже обеспечены базой. Число ключей, монета и сеть — сведения о выплате, а не деньги: им место в `raw_ref`, а не в отдельной таблице. Отдельная таблица дала бы второй журнал с собственной уникальностью и сторно — ровно то, что рамка 2 запрещает.

`raw_ref` выплаты — JSON: `{ "entry": "вручную", "keys": 5, "method": "USDT", "network": "BEP20", "note": "…" }`; `keys`, `method`, `network`, `note` необязательны. `entry: "вручную"` — признак ручного ввода; источник при этом — площадка (рамка 4).

**2. Продажа и выплата — разные события; «реализовано» — только выплаты.** Цепочка у Clover два шага: ключи проданы площадке → деньги на балансе Clover (это ещё «в работе», §16: «баланс Clover») → выплата с баланса на кошелёк владельца → **дошло до рук** («реализовано», §16). На этапе 3.2 записывается **только второй шаг**: тип `выплата Clover`. Продажу ключей на Clover мы не записываем вовсе — источника нет.

Правила итогов (тестами, задача 3):
- `реализовано` = Σ `net` выплат Clover без сторнированных, по валюте. Больше ни один тип в него не входит: ни `продажа вещи` (рынок Steam — деньги на кошельке Steam, это «в работе»), ни будущая продажа ключей.
- Число ключей из `raw_ref.keys` — справочно («ключей по выплатам»), в деньги не входит и с «Ключами Mann Co.» не сверяется (это этап 5).
- Если позже появится запись продажи ключей на Clover (новый тип — отдельное решение), она меняет только «в работе» (ключи → баланс Clover); выплата той же суммы не прибавляется к продаже. Две записи одной суммы — два события, а не два заработка.

**3. Номер транзакции.** Одно поле: хэш перевода или номер выплаты с сайта Clover — что есть у владельца. Нормализация на сервере: обрезать пробелы по краям; пробелы внутри — отказ; хэш вида `0x` + hex или 64 hex — к нижнему регистру (один перевод — одна запись при любом регистре); длина 4–200. `external_id` = нормализованный номер.

Ограничение (в интерфейсе — подсказкой у поля): одна и та же выплата, внесённая один раз номером с сайта, другой — хэшем перевода, будет двумя записями — сервер их не свяжет. Поэтому подсказка просит вносить **хэш перевода, если он есть**.

**4. Сумма и валюта.** «Получено $» — сколько дошло до рук, в долларах, с центами; хранится `net` = центы (> 0), `gross` = NULL (цены «до комиссий» у ручного ввода нет — NULL значит «нет в источнике», как у продаж Steam в чужой валюте). Комиссии `fee_*` = NULL. Только `USD`: выплата в USDT вносится долларовой суммой, монета — в `method`. Другие валюты — отдельным решением.

**5. Повтор запроса (рамка 4).** `POST /api/money/payout` идемпотентен по паре `Clover.tf + номер`:
- такой выплаты нет — запись, ответ `{ id, inserted: true }`;
- есть **действующая** (не сторнированная) с тем же номером и той же суммой — новой записи нет, ответ `{ id, inserted: false }` — панель пишет «эта выплата уже внесена». Дата не сравнивается: при повторном вводе формы позже она по умолчанию другая, а выплата та же; остаётся дата первой записи;
- есть действующая с тем же номером, но **другой суммой** — отказ `{ error: 'номер уже внесён с другой суммой: …' }` — не тихое «ок»: иначе опечатка в сумме пряталась бы за «уже внесена».

**6. Повторный ввод после сторно.** Ошибочную выплату исправляют так: сторно (с причиной) → внести заново с тем же номером. Уникальность `(source, external_id)` второй записи с тем же номером не пустит, поэтому повторный ввод получает `external_id` = `номер#2`, `#3`… — **только если все прежние записи этого номера сторнированы**. Проверка «есть ли действующая» и вставка — в одной транзакции (`begin immediate`): два одновременных запроса не создадут две действующие выплаты. Номер транзакции в показе — без суффикса; суффикс видно в подсказке строки.

**7. Сторно из интерфейса (рамка 3).** `POST /api/money/storno { id, reason }` → готовый `storno(db, id, reason, 'владелец')`. В 3.2 маршрут сторнирует **только выплаты Clover** (`type = 'выплата Clover'`, иначе отказ): сторно импортированных операций — вне этапа. Окно: что сторнируется (дата, сумма, номер), поле причины (обязательно, кнопка неактивна без неё), подтверждение словом «сторнировать». Уже сторнированная выплата в списке — с пометкой «сторнирована», без кнопки; повтор на сервере — отказ «операция уже сторнирована» (уникальность `storno:<id>`). Исходная запись остаётся.

**8. Аккаунт.** `account_id` = активный аккаунт на момент ввода — форма его называет («выплата за ключи аккаунта «…»»). Экран «Продажи» читает журнал по активному аккаунту (`useSales`), так выплата видна там же, где ключи. Ошибся аккаунтом — сторно и ввод заново.

**9. Дата.** «Когда пришло» — дата и время по часовому поясу пользователя, по умолчанию — сейчас; будущее — отказ; старше 2020 года — отказ (защита от опечатки в годе). Хранится UTC-метка.

**10. Показ.**
- Пятый узел пути денег: **«Выведено с Clover.tf»** (а не «Продано»: решение 2) — число выплат и сумма; справочно «ключей по выплатам».
- Итог «Реализовано» — сумма выплат $, число выплат; без выплат — «выплат ещё не было», не ноль.
- Правая колонка «Выплаты»: форма (номер, получено $, когда, ключей, монета, сеть, заметка) и список выплат (новые сверху: дата, $, ключей, монета/сеть, номер — сокращённо, полный в подсказке; «сторно…»).
- Показ (`VITE_DEMO=1`): две выдуманные выплаты в `dash/src/demo/sales.json`, одна из них сторнирована.
