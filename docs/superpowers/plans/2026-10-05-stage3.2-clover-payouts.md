# Этап 3.2: выплаты Clover в журнал операций (С7) — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** владелец вносит выплату Clover.tf руками на экране «Продажи»; она ложится в общий журнал `money_ops`, считается в итог «реализовано» ровно один раз, ошибочная исправляется сторно из интерфейса — с подтверждением и причиной — и, если нужно, явным исправлением, привязанным к сторнированной записи.

**Как устроено:** сервер — модуль `rig/server/payouts.ts` поверх готовых `addOp` и `storno` (`rig/server/money.ts`) и четыре маршрута (запись, исправление, сторно, список выплат); панель — форма, список выплат и окна сторно и исправления в правой колонке «Продаж»; итог «реализовано» и пятый узел пути денег — из полного списка выплат чистыми функциями `v2/sales/model.ts`. **Новой таблицы нет** (решение 1).

**Стек:** Node 24 (`node:sqlite`), Fastify; React 19 без новых зависимостей. Проверка вида — только в показе (`VITE_DEMO=1`).

**Спецификация:** §5.4 (Продажи), §7 С7, §16 (определения, журнал операций), §17 (сверка выплат — вручную). Макет: `…/2026-10-03-gemtrack-redesign/4-prodazhi.html` (форма «внести выплату», строки 229–234, 426–427). Дорожная карта: этап 3.2, ветка `feat/clover-payouts`.

**Рамки владельца (2026-10-05) — обязательны для всего плана:**
1. Только выплаты **Clover.tf**. Остальные площадки — будущие этапы.
2. Выплаты — в общем журнале `money_ops`. Второй независимый журнал не создаём; отдельная таблица — только с обоснованием (решение 1: не нужна).
3. Сторно — из интерфейса, с подтверждением и причиной. Исходная запись сохраняется, повторное сторно исключено.
4. Уникальность номера транзакции — **в пределах площадки**, а не признака «вручную». Повтор запроса не создаёт вторую выплату.
5. Выплата не увеличивает «реализовано» повторно, если соответствующая продажа уже учтена: **продажа и получение выплаты — разные события** (решение 2).

**Порядок работы:** план → сверка рецензентом → одобрение владельца → все задачи (сервер — сначала тесты, проверка мутациями) → один PR → CI и рецензия → мёрдж по «мёрдж #N». Развёртывание — отдельно, по «да» владельца. Разработка — в отдельной копии репозитория (`git worktree`): основная рабочая копия — код живого сервера.

## Global Constraints

- Деньги — целые в мелких единицах источника; у выплаты Clover — **центы долларовой суммы**, которую указал владелец (решение 4). Дробей в базе нет.
- **USDT (и любая монета) ≠ USD автоматически.** Долларовая сумма выплаты в монете — оценка владельца с отметкой источника оценки; панель никогда не подставляет её из количества монет (решение 4).
- `money_ops` не меняется и не удаляется (триггеры этапа 3.1); исправление — только сторно (`storno()`), одно на запись.
- Суммы разных валют не складываются никогда (§3.3, план 2.6 решение 2).
- Итог по неполной истории не подписывается как полный (решение 11).
- В репозиторий — никаких настоящих сумм, номеров транзакций и id: тесты и показ — на выдуманных.
- Маршруты — за общим входом и проверкой источника запроса (`auth.ts`, `gate`); в показе `post()` ничего не отправляет.
- §4.3: окна — через `useTrap` (фокус внутрь, Tab извне, возврат фокуса); смысл не только цветом.

## Решения — сверить до кода

**1. Отдельная таблица не нужна.** Всё, что нужно выплате, в `money_ops` есть: `type = 'выплата Clover'`, `source = 'Clover.tf'`, `external_id` — внутренний идентификатор (решение 3), `happened_at` — когда пришло, `currency = 'USD'`, `net` — долларовая сумма в центах, `account_id`, `created_by`, `raw_ref` — подробности ввода. Неизменяемость, запрет удаления и сторно уже обеспечены базой. Номер транзакции, версия, монета, оценка и число ключей — сведения о выплате, а не новые деньги: им место в `raw_ref`, а не в отдельной таблице. Отдельная таблица дала бы второй журнал с собственной уникальностью и сторно — ровно то, что рамка 2 запрещает.

`raw_ref` выплаты — JSON:

```json
{ "entry": "вручную", "tx": "<номер, нормализованный>", "version": 1,
  "corrects": null,
  "asset": "USDT", "assetAmount": "12.48", "network": "BEP20",
  "usdBy": "владелец", "keys": 5, "note": "…" }
```

`tx`, `version`, `entry`, `asset`, `usdBy` — обязательны; `corrects` — id сторнированной записи у исправления (решение 6), иначе `null`; `assetAmount`, `network`, `keys`, `note` — необязательны. Источник при этом — площадка (рамка 4).

**2. Продажа и выплата — разные события; «реализовано» — только выплаты.** Цепочка у Clover два шага: ключи проданы площадке → деньги на балансе Clover (это ещё «в работе», §16: «баланс Clover») → выплата с баланса на кошелёк владельца → **дошло до рук** («реализовано», §16). На этапе 3.2 записывается **только второй шаг**: тип `выплата Clover`. Продажу ключей на Clover мы не записываем вовсе — источника нет.

Правила итогов (тестами, задача 4):
- `реализовано` = Σ `net` выплат Clover без сторнированных, по валюте. Больше ни один тип в него не входит: ни `продажа вещи` (рынок Steam — деньги на кошельке Steam, это «в работе»), ни будущая продажа ключей.
- Число ключей из `raw_ref.keys` — справочно («ключей по выплатам»), в деньги не входит и с «Ключами Mann Co.» не сверяется (это этап 5).
- Если позже появится запись продажи ключей на Clover (новый тип — отдельное решение), она меняет только «в работе» (ключи → баланс Clover); выплата той же суммы не прибавляется к продаже. Две записи одной суммы — два события, а не два заработка.

**3. Номер транзакции и внутренний идентификатор — раздельно.** Номер, который вводит владелец (хэш перевода или номер выплаты с сайта Clover), хранится как есть после нормализации в `raw_ref.tx`; версия записи — в `raw_ref.version`. Внутренний `external_id` собирается из них однозначно: **`v<версия>:<номер>`** — версия только цифры, разделитель — первое двоеточие. Номер может содержать что угодно, кроме пробелов (в том числе `#` и `:`): `ABC` версии 2 → `v2:ABC`, самостоятельный номер `ABC#2` → `v1:ABC#2` — не пересекаются. Поиск «все записи этого номера» — по `json_extract(raw_ref, '$.tx') = ?` среди `source = 'Clover.tf'`, `type = 'выплата Clover'`, а не по разбору `external_id` или `LIKE`.

Нормализация на сервере: обрезать пробелы по краям; пробелы внутри — отказ; хэш вида `0x` + hex или 64 hex — к нижнему регистру (один перевод — одна запись при любом регистре); длина 4–200.

Ограничение (в интерфейсе — подсказкой у поля): одна и та же выплата, внесённая один раз номером с сайта, другой — хэшем перевода, будет двумя записями — сервер их не свяжет. Подсказка просит вносить **хэш перевода, если он есть**.

**4. Сумма: долларовая сумма и то, что пришло на самом деле, — раздельно.** Выплата Clover приходит монетой (USDT, USDC, LTC…) или фиатом — `asset` выбирается в форме, по умолчанию не выбран. Поля:
- «Пришло» — `asset` (обязательно), `assetAmount` — количество монеты как введено (строкой, необязательно), `network` (для монет);
- «В долларах» — сумма в $ с центами (обязательно). Для `asset = USD` это и есть полученное (`usdBy = 'получено'`). Для любой монеты, **включая USDT**, это **оценка владельца** (`usdBy = 'владелец'`): форма пишет у поля «ваша оценка в $ на дату выплаты», значение **не подставляется** из количества монеты и не копируется из него.

Хранится: `currency = 'USD'`, `net` = центы (> 0), `gross` = NULL (нет в источнике), `fee_*` = NULL. В показе у выплаты с `usdBy = 'владелец'` — метка `оценка` и в подсказке «оценка владельца; пришло 12.48 USDT (BEP20)». Итог «реализовано», в который вошла хоть одна оценка, — с меткой `оценка`. Автоматического пересчёта по курсу в 3.2 нет — ни для монет, ни для USD; пересчёт по курсу на дату (§5.4) — отдельная задача «история курсов».

**5. Повтор запроса записи (рамка 4).** `POST /api/money/payout` создаёт **только первую версию** номера и идемпотентен по паре «Clover.tf + номер»:
- записей этого номера нет — новая запись версии 1, ответ `{ id, inserted: true }`;
- есть **действующая** (не сторнированная) запись этого номера на **том же аккаунте** с той же суммой — новой записи нет, ответ `{ id, inserted: false }`; панель пишет «эта выплата уже внесена». Дата не сравнивается: при повторном вводе формы позже она по умолчанию другая, а выплата та же;
- действующая с другой суммой — отказ «номер уже внесён с другой суммой: $…» — не тихое «ок»: иначе опечатка в сумме пряталась бы за «уже внесена»;
- действующая на **другом аккаунте** — отказ «номер уже внесён на аккаунт «…»» (решение 8);
- все записи номера сторнированы — **отказ** «выплата с этим номером сторнирована; исправление — кнопкой «внести исправление» у сторнированной записи». Запоздавший повтор старого запроса после сторно новую действующую запись не создаёт.

**6. Исправление — явное действие, привязанное к сторнированной записи; им же переносится аккаунт.** Ошибочную выплату исправляют так: сторно (с причиной) → у сторнированной записи кнопка «внести исправление…» → форма, заполненная её данными, **включая аккаунт** (выбор из списка, по умолчанию — аккаунт исходной записи) → `POST /api/money/payout/correct { corrects: <id>, accountId, … }`. Так же исправляется и ошибочно выбранный аккаунт: исправление на другом аккаунте — это перенос, связь с исходной сохраняется в `raw_ref.corrects`, в списке у такой записи — «перенесено с аккаунта «…»».

Сервер — в одной транзакции (`begin immediate`), **в таком порядке**:

1. **Сначала — нет ли уже исправления этой записи** (запись с `raw_ref.corrects = <id>`; у одной записи исправление может быть только одно):
   - есть и действует, тот же аккаунт и та же сумма — это повтор запроса: `{ id, inserted: false }`;
   - есть и действует, но аккаунт или сумма другие — отказ «исправление уже внесено: …»;
   - есть, но **сторнировано** — отказ «исправление этой записи сторнировано; новое исправление — от него». Запоздавший повтор после сторно исправления новую запись не создаёт.
2. **Только если исправления ещё нет — можно ли создать новое:**
   - запись `corrects` — выплата Clover, и она сторнирована;
   - `corrects` — последняя версия номера (исправляют последнее, а не цепочку назад);
   - у номера нет действующей записи ни на одном аккаунте;
   - аккаунт исправления существует (`accountById` — проверяет маршрут).

Новая запись: тот же `tx`, `version = последняя + 1`, `corrects = <id>`, `external_id = v<версия>:<номер>`, `account_id` — из формы исправления. Номер транзакции в исправлении не меняется (другой номер — это другая выплата: обычный ввод). Действующая запись номера всегда одна — на всех аккаунтах вместе.

**7. Сторно из интерфейса (рамка 3).** `POST /api/money/storno { id, reason }` → готовый `storno(db, id, reason, 'владелец')`. В 3.2 маршрут сторнирует **только выплаты Clover** (`type = 'выплата Clover'`, иначе отказ): сторно импортированных операций — вне этапа. Окно: что сторнируется (дата, сумма, номер, аккаунт), поле причины (обязательно, кнопка неактивна без неё), кнопка «сторнировать». Уже сторнированная выплата в списке — с пометкой «сторнирована» и кнопкой «внести исправление…», без «сторно»; повтор на сервере — отказ «операция уже сторнирована» (уникальность `storno:<id>`). Исходная запись остаётся.

**8. Аккаунт — закреплён при открытии формы.** Форма при открытии запоминает аккаунт (id и метку) и показывает его: «выплата за ключи аккаунта «…»». Отправляется **явно**: `accountId` в теле обязателен; сервер не подставляет активный аккаунт и проверяет `accountById(accountId)` — нет такого → отказ. Сменился активный аккаунт, пока форма открыта, — форма остаётся на своём аккаунте и пишет об этом строкой («активный аккаунт сменился — выплата будет записана на «…», как показано»). Номер уже записан на другом аккаунте — отказ с названием аккаунта (решение 5): уникальность — в пределах площадки, а не аккаунта. Выплата внесена не на тот аккаунт — сторно и исправление с выбором аккаунта (решение 6).

**9. Дата.** «Когда пришло» — дата и время по часовому поясу пользователя, по умолчанию — сейчас; будущее — отказ; раньше 2020 года — отказ (защита от опечатки в годе). Хранится UTC-метка.

**10. Показ.**
- Пятый узел пути денег: **«Выведено с Clover.tf»** (а не «Продано»: решение 2) — число выплат и сумма; справочно «ключей по выплатам».
- Итог «Реализовано» — сумма выплат в $, число выплат, метки `оценка` (решение 4) и `неполно` (решение 11); без выплат — «выплат ещё не было», не ноль.
- Правая колонка «Выплаты»: форма (аккаунт — показан, номер, пришло: монета / количество / сеть, в долларах, когда, ключей, заметка) и список выплат (новые сверху: дата, $ с меткой `оценка`, пришло, ключей, номер — сокращённо, полный в подсказке, версия — «исправление №2» у версий > 1; кнопки «сторно…» / «внести исправление…»).
- Показ (`VITE_DEMO=1`): выдуманные выплаты в `dash/src/demo/sales.json` — USD, USDT с оценкой, сторнированная и её исправление.

**11. Полнота: выплаты не зависят от предела 5 000.** Экран сейчас грузит последние 5 000 операций аккаунта; выплаты и их сторно могли бы оказаться за пределом, и «реализовано» молча занизилось бы. Поэтому выплаты читаются отдельно: `GET /api/money/payouts?id=<аккаунт>` — **все** выплаты Clover аккаунта и сторно, которые на них ссылаются (`raw_ref.reverses`), без предела по числу, с флагом `complete: true`. Защитный предел маршрута — 5 000 выплат: упёрлись — `complete: false`, и итог «Реализовано» подписан «неполно: показаны последние N выплат», а не как полная сумма. Узел и итог считаются только из этого списка; общий список `/api/money` для них не используется.

- `parsePayout(body: unknown, now: number): Payout | { error: string }` — `usdBy` выводится из `asset` (`USD` → `получено`, иначе `владелец`), с клиента не принимается
- `addPayout(db, p: Payout, opts?: { now?: number; afterCheck?: () => void }): { id: number; inserted: boolean } | { error: string }` — `afterCheck` вызывается между проверкой и вставкой, только для теста гонки (как `afterInsert` у `storno`)
- `externalId(tx: string, version: number): string` → `v<version>:<tx>`

Аккаунт проверяет маршрут (`accountById`), модуль получает уже проверенный `accountId`.

- [x] **Тесты сначала** (`payouts.test.ts`, база в памяти с `MONEY_DDL`):
  - `normalizeTx`: пробелы по краям срезаются; пробел внутри — отказ; `0xABC…` и `0xabc…` — один номер; `#` и `:` внутри номера допустимы; короче 4 / длиннее 200 — отказ;

  - `addPayout`: первая — `inserted: true`, `source = 'Clover.tf'`, `type = 'выплата Clover'`, `external_id = 'v1:<номер>'`, `net` > 0, `gross` NULL, `raw_ref` — `tx`, `version: 1`, `corrects: null`, `entry`, `asset`, `usdBy`;

**Interfaces — Produces:**

- [x] **Тесты сначала:**
  - сторно выплаты — запись `сторно`, `raw_ref.reverses`, причина; без причины — отказ; второе сторно — отказ, записей сторно одна; сторно `покупки гема` этим путём — отказ; исходная запись не изменилась (все поля);
  - исправление: `ABC` v1 → сторно → `correctPayout(v1)` → v2, `external_id = 'v2:ABC'`, `corrects = id v1`;
  - **повтор исправления до его сторно:** тот же `correctPayout(v1)` ещё раз — `inserted: false`, тот же `id`, записей `ABC` две (v1 сторнирована, v2 действует); с другой суммой — отказ «исправление уже внесено»;
  - **повтор исправления после его сторно:** v2 → сторно → тот же `correctPayout(v1)` — отказ «исправление этой записи сторнировано», действующих записей `ABC` — ноль; затем `correctPayout(v2)` → v3 проходит;
  - **исправление ошибочного аккаунта:** `ABC` v1 на аккаунте A → сторно → `correctPayout(v1, accountId = B)` → v2 на B, `raw_ref.corrects = id v1`; действующая запись `ABC` одна — на B; обычный ввод `ABC` на A — отказ «номер уже внесён на аккаунт B»; повтор переноса — `inserted: false`; повтор с аккаунтом A вместо B — отказ «исправление уже внесено»;
  - исправление **несторнированной** записи — отказ; исправление не последней версии (v1, когда v2 уже есть и сторнирована) — отказ «исправляется последняя версия»;
  - исправление с другим номером — отказ «другой номер — это другая выплата»;
  - v2 → сторно → `correctPayout(v2)` → v3; действующая всегда одна.
- [x] Реализация, прогон. Мутации: разрешить сторно любого типа; убрать проверку причины; убрать «corrects сторнирована»; убрать «последняя версия»; проверять «последняя версия» раньше поиска существующего исправления (повтор до сторно перестаёт давать `inserted: false`); пропустить сторнированное исправление в шаге 1 (повтор после сторно создаёт запись) — ловятся.

## Правки после сверки (2026-10-05, вердикт по `4e0e6d1`)

1. Номер и версия раздельно: `raw_ref.tx` + `raw_ref.version`, `external_id = v<версия>:<номер>`; поиск номера — по `raw_ref.tx`. Тест: `ABC` после сторно и самостоятельный `ABC#2` не смешиваются (решение 3, задачи 1 и 4).
2. Обычный ввод создаёт только версию 1; после сторно повтор — отказ, новая версия — только явным исправлением сторнированной записи (`/payout/correct`, `corrects`). Тест запоздавшего повтора (решения 5–6, задачи 1–2).
3. Аккаунт закрепляется при открытии формы и отправляется явно; сервер проверяет его существование; номер на другом аккаунте — отказ с названием (решение 8).
4. «Пришло» (монета, количество, сеть) и «в долларах» — раздельно; у монеты, включая USDT, $ — оценка владельца (`usdBy`), без автоматического USDT = USD; утверждение «пересчёт не нужен» снято (решение 4, противоречия).
5. Предел 5 000: выплаты — отдельным полным списком `GET /api/money/payouts`; упёрлись в защитный предел — итог с меткой «неполно» (решение 11, задача 3).

## Правки после сверки (2026-10-05, вердикт по `9ff6705`)

1. Порядок в исправлении: сначала поиск существующего исправления по `corrects` (повтор → `inserted: false`; сторнировано → отказ), только потом проверки создания нового (решение 6). Тесты: повтор исправления до и после его сторно (задача 2).
2. Исправление может перенести выплату на другой аккаунт: аккаунт выбирается в окне исправления, связь — `raw_ref.corrects`, действующая версия номера одна на все аккаунты (решения 6, 8). Тест: исправление ошибочного аккаунта (задача 2).
