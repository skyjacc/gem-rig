# Этап 7: пользователи, вход через Steam, изоляция — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** друг работает в панели сам — свои рабочие аккаунты, ключ площадки, закупки, накрутка — и не видит и не трогает ничего чужого; владелец приглашает и отключает его; доступ к панели — через Tailscale.

**Как устроено:** пользователи и приглашения — новые таблицы; вход через Steam OpenID 2.0, сессия — кука на пользователя. Каждый запрос получает «кто это» (`req.user`) из сессии; один охранник владения (`own(user, accountId)`) стоит перед каждым маршрутом с аккаунтом; одиночки сервера (закупка, QR-вход, «активный аккаунт», настройки) становятся по пользователю; поток состояния собирается на каждого клиента отдельно. Три PR (решение 15): 7.1 — вход и пользователи без приглашений; 7.2 — изоляция; 7.3 — приглашения, экран «Пользователи», Tailscale, приёмка вдвоём.

**Стек:** Node 24 (`node:sqlite`, `fetch`), Fastify, React 19 — без новых зависимостей (OpenID 2.0 — прямые запросы, как прочие обращения к Steam).

**Спецификация:** §12 (несколько пользователей: 12.1–12.7, контур П1–П8), §18 (безопасность: изоляция, приглашения, OpenID, сессии), макет `8-vhod-i-polzovateli.html` (+ `8b`, `8c`). Дорожная карта: этап 7, ветка `feat/steam-auth-users`.

**Рамки владельца (2026-10-05):**
1. Приоритет — самостоятельная работа друга.
2. Личные настройки пользователей и общие ограничения сервера — явно раздельно (решение 9).
3. Изоляция: данные, токены и сессии, QR-входы, работники, закупки, поток событий (решения 5–8, 10).
4. Приёмка — два пользователя одновременно, включая обращения к чужим объектам и отключение одного (решение 14).
5. Первый доступ — Tailscale; хостинг пока не выбираем (решение 12).

## Global Constraints

- §18 — инвариант 1: пользователь A через любой маршрут, поток или текст ошибки не получает и не меняет ничего пользователя B. Проверяется тестами на **каждом** маршруте (таблица маршрутов — задача 7.2-1), а не выборочно.
- Чужой объект и несуществующий — **один и тот же ответ** (`404 нет такого аккаунта`): по ответу нельзя узнать, что объект есть у другого (решение 11).
- Пароли панель не хранит. Секреты (токены приглашений, сессии панели) — на сервере только хэшем.
- Защиты `auth.ts` (Host, Origin) остаются для всех.
- Репозиторий публичный: ни steamid, ни сумм, ни имён в коде, тестах, описаниях PR — выдуманные.
- Существующие данные не теряются и не переписываются: они становятся данными владельца (решение 4).
- `dash/dist` — живая панель: сборка туда — только развёртывание (CLAUDE.md).

## Решения — сверить до кода

**1. Пользователи и приглашения (П1, §18).** Таблицы в базе:
- `users (id, steamid unique, name, role ('владелец'|'пользователь'), limits_json, disabled_at, created_at)`;
- `invites (id, token_hash unique, name, limits_json, expires_at, created_by, created_at, used_at, used_by_steamid, revoked_at, revoked_by, attempts)`;
- `sessions (id, token_hash unique, user_id, created_at, last_seen_at, revoked_at, user_agent)`.

Токен приглашения — 32 случайных байта (256 бит, §18: не меньше 128), в базе — только SHA-256; срок 1 / 7 / 30 дней; одноразовый; отзыв; использованное не перепривязывается никогда. Попытки по неверному токену — счётчик и ограничение (5 в минуту с адреса).

**2. Вход через Steam OpenID 2.0 (П2, §18).** Кнопка «Войти через Steam» → `https://steamcommunity.com/openid/login` с `openid.mode=checkid_setup`, `return_to` = внешний адрес панели + `/api/auth/steam/return`, `realm` = внешний адрес. При возврате сервер проверяет **всё** из §18:
- `openid.op_endpoint` — ровно `https://steamcommunity.com/openid/login`;
- `openid.return_to` — ровно наш адрес возврата (с нашим одноразовым `state` в нём);
- `openid.claimed_id` — `https://steamcommunity.com/openid/id/<17 цифр>`, `identity` = `claimed_id`;
- подпись — запросом `check_authentication` к Steam (ответ `is_valid:true`);
- `openid.response_nonce` — запоминается и повторно не принимается (и не старше 5 минут).

Детали адресов и полей сверяются с документацией Steam и спецификацией OpenID 2.0 **при реализации** (§12.4) — в тестах ответы Steam подменены, вживую вход проверяется на шаге приёмки. Внешний адрес панели — из окружения `PANEL_URL` (§12.5), не из заголовка `Host`.

**3. Сессии (П2).** После входа — новая сессия: кука `rig_auth` (как сейчас: `HttpOnly`, `SameSite=Strict`, `Secure` по HTTPS) со случайным токеном; в базе — хэш. «Выйти на всех устройствах» отзывает все сессии пользователя. Отключение пользователя отзывает все его сессии сразу (решение 10). Старый общий токен: **запасной вход только владельца**, пока его steamid не привязан; после привязки и отдельного решения владельца снимается (7.3).

**4. Владение данными (П3).** У рабочего аккаунта в реестре — `user` (id пользователя). Переход: все существующие аккаунты, журнал, ключи, настройки — владельца; таблица `users` получает владельца при первой привязке его Steam через токен (§12.4). `money_ops.user_id` новых записей — id пользователя, старые `'owner'` = владелец (сопоставление, не перезапись: журнал неизменяем). «Активный аккаунт» — свой у каждого пользователя (`users.active_account`). Один и тот же steamid рабочего аккаунта у двух пользователей — запрещён (отказ без названия чужого: решение 11).

**5. Охранник владения (П4).** Одна функция `own(user, accountId): Account | null` — аккаунт этого пользователя или `null`. Каждый маршрут с аккаунтом (явным `id` или активным) идёт через неё; `null` → `404 нет такого аккаунта`. Маршруты без аккаунта делятся на три вида — каждый явно в таблице задачи 7.2-1:
- **свои** — данные текущего пользователя (через его активный аккаунт);
- **общие открытые** — карта матчей, каталог гемов, `supply`, цена ключа (§12.3) — без данных пользователей;
- **только владельцу** — экран «Пользователи», общие ограничения сервера, перезапуск.

**6. Поток событий (П4).** `/api/stream` хранит клиента вместе с его пользователем; состояние собирается **на каждого пользователя отдельно** (`buildState(user)`) и уходит только его клиентам. Общие тяжёлые части (`slow()`: каталог, ключи) считаются один раз и делятся — в них нет данных пользователей. Отзыв сессии и отключение пользователя закрывают его открытые потоки.

**7. Одиночки сервера — по пользователю (П5, П3).**
- **Закупка:** `job` — на пользователя (`Map<userId, Job>`); остановка — только своей. Общий ограничитель площадки — по ключу, как сейчас (С0): у каждого свой ключ.
- **QR-входы игры и веба:** `link`/`webLink` — на пользователя; «одна привязка за раз» — в пределах пользователя. Ссылка на код (`link.url`) уходит только его клиентам (решение 6) — это закрывает утечку, которая сейчас есть у З1.
- **Работники:** уже по аккаунту; маршруты — через охранник; стоп и автопилот — только своих.

**8. Токены и файлы сессий Steam.** Файлы `token-*.json` лежат в общей папке `tools/gcwatch` — имена по id аккаунта; id аккаунта уникален на сервере (решение 4), значит конфликтов имён нет. Панель их содержимое никогда не отдаёт (как сейчас). Отвязка и отключение пользователя удаляют/гасят только его файлы и процессы.

**9. Настройки: личные и общие ограничения сервера (П6, рамка 2).**

| Поле | Чьё | Почему |
|---|---|---|
| `goal`, `sellPrice`, `perGem`, `priceTolerance`, `purchaseCap`, `spread.*`, `pace.ceil`, `pace.enough`, `pace.clean`, `pace.down`, `pace.up` | **личное** | экономика и темп своей работы |
| `pace.floor` | **общее ограничение** + личное не ниже | нижняя пауза защищает игровой координатор и общий адрес ПК (решение 13); личное значение может быть только строже |
| `tick`, `silentLimit`, `startLimit`, `maxFailures` | **общее** (только владельцу) | работа сервера и его отправщиков, нагрузка на общий ПК |
| `invTtl`, `invStale` | **общее** | частота чтения Steam с общего адреса (решение 13) |
| `treeTop` | **общее** | вид дерева, считается общим |

Хранение: общие — как сейчас `tools/settings.json` (владелец); личные — `users.settings_json` поверх значений по умолчанию. Действующее значение = личное, зажатое общими пределами (тест: личный `pace.floor` ниже общего → действует общий). «Настроить» у пользователя показывает и меняет только личные; у владельца — ещё и вкладку общих.

**10. Лимиты и отключение (П7, рамка 4).** У пользователя: предел рабочих аккаунтов (по умолчанию 3) и одновременно работающих отправщиков (по умолчанию 1); задаются в приглашении и на экране «Пользователи». Отключение пользователя — одним действием, по порядку: отзыв всех сессий → закрытие его потоков → стоп его работников и отправщиков → стоп его закупки → отмена его QR-входов. Повторный вход отключённого — «доступ отключён владельцем». Данные не удаляются. Включение обратно — владельцем.

**11. Тексты ошибок без утечек.** Ни одна ошибка не называет чужой аккаунт, метку, steamid, сумму или само существование чужого объекта:
- чужой и несуществующий аккаунт — одно и то же «нет такого аккаунта»;
- QR-вход Steam, уже привязанного у **другого** пользователя, — «этот Steam привязать нельзя» (без «уже привязан как «…»» — так сейчас для своих);
- выплата Clover с номером, внесённым **другим** пользователем, — сейчас «номер уже внесён на аккаунт «…»» (план 3.2): становится «этот номер транзакции уже внесён» без метки; метку видно, только если аккаунт свой.

Тест на каждую ветку: ответ B не содержит ни метки, ни steamid, ни id объектов A.

**12. Доступ через Tailscale (рамка 5).** Сейчас панель слушает только `127.0.0.1`, `tailscale serve` не настроен. Предлагается:
- панель остаётся на `127.0.0.1:4322`; наружу в tailnet её отдаёт `tailscale serve` по HTTPS (`https://<машина>.<tailnet>.ts.net` → `http://127.0.0.1:4322`) — порт панели в сеть напрямую не открывается;
- другу машина **делится** (Tailscale «Share») — он видит только её, не остальной tailnet; ACL ограничивает доступ к ней портом 443;
- `PANEL_URL` = этот HTTPS-адрес (нужен OpenID: `return_to`, `realm`); имя уже есть в `ALLOWED_HOSTS`.

Это действия владельца в его учётной записи Tailscale — делаются по шагам на этапе 7.3, с его «да». Что проверить до этого (`OPEN`): видит ли получатель общей машины её по тому же имени `*.ts.net` (иначе `PANEL_URL` и `ALLOWED_HOSTS` для него другие) и работает ли HTTPS `tailscale serve` для общей машины.

**13. Общий ПК — ограничения (рамка 6), пишутся другу словами и в экран «Пользователи».**
- **Всё работает на ПК владельца**: отправщики друга — процессы на нём; ПК выключен, спит или без сети — работа друга стоит. Перезапуск панели владельцем перезапускает и работу друга.
- **Один внешний адрес**: игровые входы и чтения Steam всех пользователей идут с одного IP. Ограничитель частоты Steam (`steamweb`/инвентарь) — общий на адрес: чтения друга расходуют общий запас. Связь аккаунтов разных людей по общему IP для Steam — риск, который мы проверить не можем.
- **Нагрузка**: каждый работающий отправщик — процесс Node; предел одновременных — решение 10.
- **Доверие (§12.7)**: сессии Steam и ключ площадки друга лежат на ПК владельца; интерфейс их не показывает, но владелец ПК технически может до них добраться. Это доверие, а не защита — сказать другу до приглашения.
- **Площадка**: ограничитель market.dota2.net — по ключу (у каждого свой) — друг владельцу запас не расходует.

**14. Приёмка вдвоём (рамка 4).** Автотесты (7.2) и живая приёмка (7.3) — два пользователя **одновременно**, у каждого рабочий аккаунт, у обоих открыт поток:
- B обращается к **каждому** маршруту с id аккаунта A (и подставляя чужой id выплаты, сторно, QR-входа) → 404 «нет такого аккаунта», в базе и процессах A ничего не изменилось;
- поток B за время работы A (закупка, отправки, QR-вход) не содержит ни одного объекта, метки, steamid или суммы A; и наоборот;
- ошибки B (решение 11) не раскрывают данных A;
- B не может остановить работника или закупку A, отменить QR-вход A, поменять общие ограничения;
- **отключение B** посреди работы: его сессии и поток закрыты сразу, работники и закупка остановлены, следующий запрос — 401, повторный вход — «доступ отключён»; работа A не прерывается;
- лимиты B (аккаунтов, отправщиков) соблюдаются.

**15. Три PR.**
- **7.1 — вход и пользователи** (без приглашений): таблицы, OpenID, сессии, владелец привязывает свой Steam через токен; поведение панели для владельца не меняется. Друга пустить ещё нельзя — нет изоляции.
- **7.2 — изоляция**: охранник владения на всех маршрутах, поток по пользователю, одиночки по пользователю, настройки личные/общие, лимиты, тексты ошибок, автоприёмка вдвоём (решение 14, тестами).
- **7.3 — приглашения и доступ**: приглашения, экран «Пользователи», отключение, Tailscale по шагам с владельцем, живая приёмка вдвоём (второй пользователь — тестовый Steam владельца, **не друг**), затем решение о снятии входа по токену. Приглашение друга — только после этой приёмки и отдельного «да».
