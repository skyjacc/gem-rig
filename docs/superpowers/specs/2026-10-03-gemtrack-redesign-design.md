## 0. Как читать

Документ для двоих.

**Агенту**, который будет это строить или чинить без памяти о разговоре, нужны все разделы.
Порядок такой: правила (§3) → каркас (§4) → экраны (§5) → откуда данные (§6) →
что доделать на сервере (§7) → карта файлов (§8) → проверка (§9) → ремонт (§10).
Для серверной части и денег — ещё §12–§19: пользователи, риск, инварианты, источники истины,
деньги, сверка, безопасность, диагностика. **Инварианты §14 важнее всего остального.**

Если код и документ расходятся, сначала понять, какого рода факт (§15):

- **как система работает сейчас** (адреса API, формулы, правила робота) — прав код и тесты; поправить документ;
- **какой должна стать панель** (вид, поведение, правила §3 и инварианты §14) — прав документ;
  код — недоделка или регресс;
- **внешний факт** (комиссии Steam, правила Steam, лимиты площадки, API Clover) — прав только
  первоисточник с датой проверки. Ни код проекта, ни этот документ внешний факт не доказывают;
- непонятно, что из трёх — **остановиться и спросить владельца**, а не «чинить» одно под другое.

Утверждения в документе помечены так же, как в README: `VERIFIED` (проверено по коду или
первоисточнику), `OBSERVED` (живой замер), `HYPOTHESIS` (вывод без проверки), `CONFLICT`
(источники расходятся). Где пометки нет — это решение по дизайну, а не факт.

У `VERIFIED` всегда есть источник и дата проверки, у `OBSERVED` — дата и где наблюдалось.

## 1. Зачем

Нынешняя панель снята с osint-catalog.xyz: чёрный фон, прямые углы, серый текст 10–12 px.
К октябрю в ней накопилось:

1. **Два стиля спорят.** Экран входа и активный пункт меню — синий «портал» со свечением,
   всё остальное — серый каталог. Главная кнопка «накрутить» при этом жёлтая, цвета «внимание».
2. **CSS собран заплатками.** `.lg-card`, `.lg-go`, `.lg-float` объявлены дважды, поздние
   правила перебивают ранние. Понять, какое правило действует, можно только в браузере.
3. **Нет пустых состояний.** Без данных Скупка и инвентарь бесконечно показывают скелетон.
4. **Иерархии нет.** На Пульте всё одного веса, главное («стоит / идёт», «0 из 51 готово») не выделено.
5. **Граф** — отдельная вкладка с почти пустым экраном, хотя связь «аккаунт → гемы → вещи»
   и есть устройство всей работы.
6. **Главного итога работы в панели нет.** Деньги идут гемы → рынок Steam → ключи Mann Co. →
   Clover.tf, а панель видит только первую часть.

## 2. Что меняется — коротко

- **Новый визуальный язык** по референсам (Dribbble: Control AI, Haulix, PicGen, Quarn):
  графит вместо чёрного, слои-карточки со скруглением, один лаймовый акцент со свечением.
- **Шесть экранов вместо пяти:** Обзор, Инвентарь, Скупка, **Продажи** (новый), Аккаунты, Журнал.
- **Обзор = бывший Пульт + Граф.** В центре холст «аккаунт → гемы → вещи», справа инспектор.
- **Инвентарь — отдельный экран:** стопки одинаковых вещей, связки гемов, все аккаунты.
- **Скупка вокруг робота:** конвейер «план → покупка → приход» с лентой покупок.
- **Плавающий пульт снизу на всех экранах:** статус работника и «Накрутить» под рукой.
- **Каждая цифра подписана**, откуда она: `инвентарь`, `журнал`, `карта`, `выписка`, `оценка`.
- **Вход через Steam и несколько пользователей:** друг входит своим Steam по приглашению и работает
  со своими аккаунтами отдельно; владелец видит экран «Пользователи» (§12).

### Решения, принятые по ходу обсуждения

| Вопрос | Решение | Почему |
|---|---|---|
| Глубина | Полная переработка: стиль и устройство экранов | выбрано явно |
| Направление | Графит + слои + один акцент, по референсам | выбрано из макетов A/B/C, затем по шотам Dribbble |
| Акцент | Лайм `#b8f25c` | у всех графовых референсов зелёное свечение связей; синий остаётся только на экране входа |
| Компоновка | «Холст — главный экран» (вариант A из трёх) | рекомендовано; B оставлял Граф «картинкой по случаю», C тесен для таблиц |
| Карта «потолок × цена» в Скупке | **Убрана** | «странная и непонятная» |
| Колонка «отправок» в Скупке | Переименована в «доп. время накрутки», главная цифра — время | число отправок без пояснения было непонятно |
| Цель счётчика | **≈ 1 000**, а не 2 000 | так реально работают; в снимке стоит 2 000 |
| Продажи | Отдельный экран | Скупка тратит деньги, Продажи их возвращают — главный итог |
| Второй человек | Раздельно, вход через Steam + приглашение, экран «Пользователи» у владельца | §12 |

## 3. Правила, которые нельзя нарушать

### 3.1 Никаких прыжков

Наведение и выделение **не меняют размер и положение** ничего на экране.

- наведение — только цвет фона: слой `--s2` → `--s3`;
- выбор — кольцо акцентом **внутрь**: `box-shadow: inset 0 0 0 1px var(--ac)`;
- запрещено: `transform` на hover, смена `border-width`, смена `padding`, `font-weight` в выделении;
- цветная полоса слева у тревоги — тоже тень (`inset 3px 0 0 <цвет>`), а не `border-left`:
  иначе текст съедет на 3 px.

История: в первом макете блоки подпрыгивали, потому что класс `.card` совпал с классом
инструмента показа, а у того на hover стоял `translateY(-2px)` и на выбор `border-width: 2px`.
Пользователь заметил сразу. Проверка — §9.3.

### 3.2 Цель счётчика — только из настроек

Число «1 000» (или любое другое) **нигде не пишется в разметке**. Везде `settings.goal`
(`/api/settings`, поле `goal`). От него считаются: «дойдёт / не дойдёт», «готово к продаже»,
полосы и кольца прогресса, «доп. время» в Скупке, «до цели» в карточках.

Пример, почему это важно: у Ohaiyo 1 849 матчей. При цели 2 000 он «не дойдёт» и висит
тревогой, при цели 1 000 — нормальный гем.

### 3.3 Каждая цифра честная

- Если число — оценка, рядом метка `оценка` (жёлтая).
- Если число со слов человека (введено руками) — метка `со слов` (синяя).
- Если данных нет — прочерк и объяснение, **а не ноль и не выдумка**.
- Источник подписан маленькой меткой: `инвентарь`, `журнал`, `карта`, `очередь`, `граф`,
  `выписка`, `api.clover.tf`.
- У каждого значения одно из четырёх состояний, и выглядят они по-разному:

  | состояние | вид | пример |
  |---|---|---|
  | известно | обычное число | `51 вещь` |
  | оценка | `≈` и метка `оценка` | `≈ 7 вещей` |
  | устарело | серее + время снимка | `$1.66 · 18 мин назад` |
  | нет данных | прочерк + причина | `— площадка не ответила` |

- У внешних и денежных значений (цены, баланс, курс, инвентарь Steam) — **время**: «обновлено 16:47»
  рядом или в подсказке. Глобальной плашки «данные устарели» для них мало.
- **Данные противоречат друг другу** — отдельное состояние, не «нет данных»: например, Steam показывает
  13 ключей, а журнал — 12. Жёлтая плашка «расходится с …» и кнопка «сверить заново» (§17).

### 3.4 Безопасность действий

- «Накрутить» тратит матчи навсегда. Кнопка в плавающем пульте **идёт через то же окно
  подтверждения**, что сейчас (`dash/src/parts/Confirm.tsx`). Не убирать.
- Запуск закупки — только кнопкой человека. Робот закупки не стартует по расписанию
  (в сервере так и есть, менять не надо).
- Отвязка аккаунта — окно с подтверждением вводом имени аккаунта. Единственный аккаунт
  отвязать нельзя (сервер ответит «это единственный аккаунт»), кнопка неактивна с подсказкой.
- Ключи площадки и токены на экран не выводятся, только статус.

### 3.5 Числа

- Цифры — шрифт **Geist** с `font-variant-numeric: tabular-nums`, **не** Geist Mono.
  В Geist Mono пробел между разрядами шириной в целую цифру, «1 946» разваливается на «1  946».
- Geist Mono — только для идентификаторов: steamid, assetid, номер матча.
- Цены меньше $0.10 — три знака после точки ($0.012). Полцента не должно стать нулём.
- Разделитель разрядов — пробел (`toLocaleString('ru-RU')`).

## 4. Каркас

### 4.1 Токены

```
фон            --bg  #0c0c0e   (страница)
слой 1         --s1  #141416   (панели, рейка, пилюли)
слой 2         --s2  #1b1b1e   (всё внутри панели: плитки, строки, поля)
слой 3         --s3  #232327   (наведение, чипы)
кромка         --line #ffffff0f   только у панелей; у плиток кромки нет — они отличаются фоном
кромка+        --line2 #ffffff17  плавающие элементы, узлы холста
текст          --ink #ecebe8 / --ink2 #a7a5a0 / --mute #76746f
акцент         --ac  #b8f25c   «идёт / готово / главное действие»
внимание       --warn #f2b44a
стоп           --stop #ff7a7a
скругления     16 — панель · 10 — всё внутри панели · 999 — пилюли, чипы, кнопки, рейка
отступы        сетка 4: 16 внутри панели и между панелями, 8 между плитками
текст          12 подписи · 13 основной · 15 заголовок секции · 22–24 заголовок экрана · 20/34 большие цифры
движение       150 мс на цвет; появление 220 мс; никаких анимаций размера
```

Цвета смысла — только три: акцент, внимание, стоп. Четвёртого нет.

- **Рейка:** логотип-гем с лаймовым свечением; капсула из шести круглых кнопок:
  Обзор, Инвентарь, Скупка, Продажи, Аккаунты, Журнал. Внизу отдельной капсулой — Общие правила.
  Активная — светлый круг с тёмной иконкой. Подписи — всплывающие при наведении.
- **Верхняя полоса:** переключатель аккаунта (аватар, имя, лампа) и 4–6 KPI-пилюль своего экрана;
  справа плашки состояния: «данные устарели», «показ — снимок», колокольчик тревог со счётчиком.
- **Плавающий пульт** — на всех экранах, по центру снизу страницы: лампа + «стоит / идёт» + причина,
  пауза, темп, до конца, последнее подтверждение, «настроить», «▶ Накрутить» (лайм, со свечением;
  во время работы — серая «Остановить»).
- **Правая колонка** у каждого экрана своя: инспектор выбранного, корзина, работник.

### 4.3 Клавиатура и доступность

Есть в нынешнем CSS и **не должно потеряться** при переписывании: `:focus-visible` (видимая
рамка фокуса) и `prefers-reduced-motion` (без анимаций). Дополнительно:

- всё, что кликается, достижимо `Tab`, срабатывает на `Enter`/`Space`; окна закрываются `Esc`
  (кроме подтверждения «Накрутить», §5.7);
- в холсте Обзора — стрелки переводят выбор между узлами, `Enter` открывает инспектор;
  режим «список» (§5.1) — полный заменитель холста;
- подсказки, которые сейчас только при наведении, доступны и с фокуса;
- смысл не передаётся только цветом: у «не дойдёт / стоп» есть слово или значок;
- у кнопок-иконок (рейка, зум) есть подписи для чтения с экрана.

## 5. Экраны

Для каждого: зачем, что на экране, откуда данные, пустые состояния.

### 5.1 Обзор — `1-obzor.html`

**Зачем:** ежедневный экран. Работает ли, что с гемами, что требует внимания.

- **Холст** с точечным фоном: узел аккаунта слева → столбец узлов гемов → веер вещей
  выбранного гема справа.
  - Узел гема: иконка, имя, счётчик «54 / цель», полоса прогресса, вторая строка — герой и
    число вещей или чип проблемы («не дойдёт», «нет в карте»).
  - Рёбра: обычные — тонкие серые; при работе — лаймовые со свечением и бегущим импульсом;
    «не дойдёт» — жёлтый пунктир; «не настроен» — красный пунктир. Легенда в углу.
  - Веер: до 4–5 вещей + «ещё N — в инвентаре». Подпись ребра «4 вещи · +1 за матч».
  - Переключатель «дерево / сеть матчей / список». Сеть — нынешний режим `Graph.tsx`.
    **Список** — обычная таблица гемов: на случай, когда аккаунтов и гемов станет много
    и граф превратится в кашу, и для работы с клавиатуры.
  - Зум справа: +, −, вписать. Холст вписывается в видимую область сам.
- **Инспектор справа:** иконка гема, кольцо прогресса к цели, факты (разброс по вещам,
  осталось до цели, дойдёт ли), список вещей, кнопки «только этот гем», «в инвентаре».
- **Тревоги с кнопками** под инспектором: «DD — до цели не дойдёт» → «снизить цель до 568»,
  «не считать товаром»; «CaspeRRR — непонятно, чьи матчи считать» → «указать команду».
- **Данные:** `state.mine` (гемы и вещи), `/api/graph`, `/api/tree`, `state.autopilot`,
  `/api/settings`. Тревоги — те же вопросы, что сейчас в блоке «Требует внимания» на Пульте.

### 5.2 Инвентарь — `2-inventar.html`

**Зачем:** что лежит, что дойдёт до цели, что можно продавать.

- **Сводка:** «готово к продаже X / N» с полосой из трёх частей (готово · дойдут · не дойдут),
  «дойдут при этой работе», «не дойдут», «сожжено» (с подписью «у аккаунта такого-то»).
- **Связки** — пары гемов, которые поднимаются одной отправкой, с числом общих матчей
  (из `/api/graph` → `edges[].shared`). Пояснение: одна отправка матча даёт +1 всем гемам
  этого матча (README §2). Клик по паре фильтрует вещи только этих двух гемов.
- **Фильтры-чипы со счётчиками:** все · дойдут · не дойдут · готово · есть копии. Поиск.
- **Отсеки по гемам:** шапка (иконка, герой, вещей, надето, матчей у команды/игрока,
  «вместе с: Team Empire 217 · NaVi 76», лучший счётчик с полосой). Сворачивается.
- **Ячейки** с пунктирной кромкой (образ — грузовой отсек Haulix). **Одинаковые вещи —
  одна стопка** «×5» с сегментами копий «12 · 12 · 0 · 0 · 0», надетая обведена.
- **Карточка справа:** большая иконка со значком «×N», шкала счётчика с **отметкой потолка
  команды**, факты, панель «Копии» по аккаунтам, панель «Поднимается вместе с».
  Если у копий разные счётчики — пояснение с меткой `оценка`: копии с нулём, скорее всего,
  пришли после того, как матчи уже сгорели (README §4.1, §4.7).
- **Переключатель «все аккаунты / конкретный».** Требует доработки сервера (§7, С3):
  сейчас `state.mine` строится только по активному аккаунту.

### 5.3 Скупка — `3-skupka.html`

**Зачем:** запустить робота, который покупает гемы на market.dota2.net, и видеть, как он работает.

- **Робот закупки — конвейер из трёх узлов** (связаны линиями, как на Обзоре):
  План (лотов, сумма) → Покупка (куплено) → Приход в Steam (пришло, вердикты сканера
  «чисто / наш / выигрыш»). Во время работы узлы подсвечены, по линиям бегут импульсы.
- **Строка прогресса:** «куплено X из Y», «потрачено $ из потолка $», «сейчас: Alliance ·
  лот 19 из 25 · позиция 3 из 6», кнопка «Остановить».
- **Лента покупок справа в конвейере:** каждый лот — ✓ куплен / ↑ цена выросла, позиция брошена /
  ↻ площадка не ответила, повтор N из 3; две цены — по плану и в момент покупки.
  Источник — `state.purchase.log` (`PurchaseRun`).
- **План** ниже: строки гемов (иконка, цена, за 1000, потолок с отметкой цели, общие матчи
  с аватарками моих гемов, лотов, **доп. время накрутки**, степпер «− N +»).
  - «Доп. время»: главная цифра «+7 мин», под ней «522 отправки».
    Формула сервера: `max(0, min(pool, goal) − min(overlap, goal))`, для гемов в работе — 0
    (`rig/server/api.ts`, строка с `const sends`). Время = отправки / 76 в минуту (замер, `Buy.tsx`).
    Подсказка на ячейке расшифровывает расчёт. Пример при цели 2 000: «2 000 − 1 478 общих матчей =
    522 отправки; при 76 в минуту это 7 мин». При цели 1 000 тот же гем — 0: общих больше цели.
  - В макете «общие матчи» у новых гемов оценены суммой пересечений по парам из графа снимка —
    это завышает. В панели брать число, которое считает сервер (`overlap` в `/api/market`).
  - Гемы, что уже крутятся, — «бесплатно · уже крутится», строка подсвечена.
  - Сортировка по умолчанию = порядок «собрать план»: в работе → больше общих → дешевле тысяча → дешевле лот.
  - Во время работы робота степперы заблокированы.
- **Справа:** «Закупка на» (аккаунт и статус ключа площадки; без ключа — красная плашка и
  пояснение, что сервер не даст запустить), «Бюджет — он же потолок суммы» с правилами отбора
  словами, «Корзина» (строки, спишется, самоцветов, доп. время, допуск цены 0 %) и
  «Запустить закупку».
- **Правила робота** (из `rig/server/purchase.ts`, менять не надо): перед каждым лотом свежая
  цена; дороже плана с допуском `priceTolerance` (по умолчанию 0) — позиция бросается;
  нет денег или неясно, списались ли — стоп всего; отказ площадки — до 3 повторов подряд;
  не больше `perGem` (25) лотов одного гема.

### 5.4 Продажи — `4-prodazhi.html` (новый экран)

**Зачем:** главный итог — сколько реальных денег принесла работа.

Цепочка, как она устроена у владельца:
гемы на market.dota2.net → накрутка до цели → продажа на рынке Steam (комиссии — §16; у Dota 2 в FAQ Steam: 5 % Steam + 10 % игре, `VERIFIED`: FAQ Steam «Community Market», 3 окт 2026) → на деньги кошелька
покупаются ключи Mann Co. (их можно продать за реальные деньги, кошелёк — нет) → ключи ждут, пока станут
передаваемыми → продажа на Clover.tf за крипту.

- **Путь денег — пять узлов:** Гемы куплены (валюта площадки) → Продано на Steam (вещей, пришло
  на кошелёк — в валюте кошелька) → Куплено ключей (шт, цена ключа — в валюте кошелька) → Ждут анлока
  (шт, ближайшая дата) → Продано на Clover.tf ($). Валюты берутся из данных (`currency` у площадки,
  валюта кошелька Steam), в разметке не пишутся.
  Последний узел подсвечен акцентом. Под узлами итог «вложено ₽ → выведено $».
- **Кошелёк Steam по дням:** столбцы вверх — продажи гемов (акцент), вниз — покупки ключей
  (серые) и прочие покупки (бледные). Подсказка с суммами за день.
- **Ключи Mann Co.:** сверху — **на руках · на hold · можно передать сейчас** и ближайшая дата освобождения
  (из инвентаря TF2 своей сессией Steam, §7 С5); ниже — партии покупок: дата, штук, цена, сумма,
  «можно» / «через N дн · дата». До подключения С5 даты — оценка «7 дней после покупки».
- **Продажи гемов по дням:** вещей, сколько заплатил покупатель, комиссия Steam, комиссия игры, сколько
  пришло на кошелёк — **четыре отдельных числа из истории рынка**, а не пересчёт «×1,15». Пока истории
  нет (§7 С4) — только «пришло», остальное прочерком.
- **Валюта — из кошелька аккаунта** (`wallet.currency`), не из макета. ₴ в макете — пример.
- **Три итога вместо одного «вложено → выведено»** (определения — §16): реализовано (дошло до рук),
  в работе (гемы, вещи, кошелёк, ключи, баланс Clover — по оценке с датой), вложено.
- **Отчётная валюта — доллар.** Вложено (валюта площадки), продажи (валюта кошелька) и выплаты ($)
  приводятся к $ по курсу **на дату операции**; у пересчитанного числа метка `оценка` и курс в подсказке.
  Источник курсов — уже есть в коде: курс НБУ и курс, выведенный из цен площадки (`market.ts`,
  `nbuRate`, `impliedRate`).
- **Справа — «Куда продать ключи».** Несколько площадок, отсортированы по тому, **сколько придёт на руки
  за твоё число свободных ключей**, а не по цене за штуку. У каждой площадки (модель — §16):

  | поле | что это |
  |---|---|
  | цена за ключ | число |
  | тип цены | **мгновенно** (площадка покупает сама) · **заявка** (лучший ордер в стакане) · **витрина** (цена выставленных лотов — столько получишь, только если купят) |
  | комиссия | продавца и/или вывода |
  | на руки за N | с учётом комиссии **и глубины**: если мгновенно берут меньше N — так и написано («сразу только 20») |
  | выплата | лучший **из принятых тобой** способов этой площадки: монета + сеть (USDT BEP20, USDT ERC-20…), PayPal, банк — и его комиссия |
  | источник | `API` · `страница` · `вручную`, и время проверки |

  **Способы выплаты — все, что есть у площадки**, а не переключатель «крипта / PayPal». Сверху ряд
  «Принимаю:» — чипы способов, собранные со всех площадок (PayPal, банк, USDT, USDC, LTC, BTC, ETH, SOL,
  «ещё…»); выбор хранится в настройках пользователя. Для каждой площадки берётся лучший из выбранных
  способов; монета считается совпавшей только **вместе с сетью** (USDT у Belethor есть только в BEP20,
  у Merchant.TF — только в ERC-20). Если комиссия способа заранее неизвестна — сумма «до комиссии сети»
  с меткой.

  **Слежение** — панель сама проверяет каждую площадку по расписанию (не чаще раза в 10–15 минут) и
  хранит: цену, тип цены, глубину (сколько берут по этой цене), комиссии по способам выплаты, время
  проверки. Тревоги в колокольчик: сменилась лучшая площадка для твоего числа ключей; цена ушла больше
  чем на порог; глубины меньше, чем у тебя свободных ключей; изменилась комиссия способа выплаты; площадку
  не удалось прочитать (её цифры становятся «устарело», а не остаются как свежие).

  Площадки на старте (проверено 2026-10-03, §20): Clover.tf, Merchant.TF, instant.tf, Belethor,
  Mannco.store. CS.Deals — только после ключа API (их API требует ключ аккаунта и не отдаёт мгновенную
  цену выкупа). Расширение списка — отдельная задача, не в этой работе.
- **Выплаты:** история выплат у Clover есть только на сайте после входа — в API её нет
  (`VERIFIED`: публичный API отдаёт только цены). Форма «площадка · ключей · получено $ · способ выплаты ·
  номер транзакции · + внести выплату». Номер транзакции обязателен и уникален в паре с площадкой —
  одна выплата не может быть внесена дважды. Записи не редактируются задним числом: ошибка исправляется
  сторнирующей записью (§16).
- **«Что подключить»** — честный список: что уже идёт само, что требует доработки (§7).
- **Пока не подключено** (§7), экран показывает пустые состояния с объяснением, а не нули.

### 5.7 Окна и служебные состояния — `7-okna-i-sostoyaniya.html`

- **Подтверждение «Накрутить»** — список последствий, а не «вы уверены?» (как сейчас в
  `Confirm.tsx` + `preview()` в `Work.tsx`): гемы в работе, в очереди, сколько отправок,
  докуда вести гем, срок, пауза, цель. Строки «до конца очереди» и «весь запас» — жёлтые.
  Красный блок: матч расходуется навсегда, вернуть нельзя ни остановкой, ни отвязкой; на другом
  аккаунте он свежий. Кнопка лаймовая, при нажатии — «запускаю…». **Закрывается только кнопками**,
  не по клику на фон и не по Esc — чтобы не закрыть в момент решения.
- **«Настроить» из пульта** — боковое окно справа (как `Modal side` сейчас), две вкладки:
  - «этот аккаунт»: сколько отправок (100 · 500 · 2 000 · всё · своё), работать до (без срока ·
    2 ч · 8 ч · до 10 утра), докуда вести каждый гем (весь запас · 500 · 1 000 · 1 500 · 2 000),
    разброс, пауза (к сроку · сама · 0,5–30 с), гемы чипами. Применяется сразу — как сейчас;
  - «общие правила»: 20 полей из `Tune.tsx` (`RULES`) группами «Цель и деньги», «Работник»,
    «Темп», остальное под «показать все». Изменённое поле — жёлтая кромка; внизу «изменено N»,
    «сбросить», «Сохранить».
- **Колокольчик** — выпадающий список тревог с любого экрана: сначала то, из-за чего работа стоит
  (красные), потом «не дойдёт» (жёлтые), потом справочные. У каждой — кнопки действия; решённая
  исчезает. Пусто — «Всё в порядке».
- **Первый запуск** (аккаунтов нет) — объяснение, три шага, «Привязать аккаунт».
- **Запуск панели** — логотип дышит, «соединяюсь с сервером…».
- **Сервер не отвечает** — что делать: `cd rig && npm run server` на домашнем ПК, «Проверить ещё раз»,
  сколько без связи.
- **Данные устарели** — числа остаются, но серее, с плашкой времени снимка; живое «идёт»
  становится «идёт?». Плашка «данные устарели — N без связи» в верхней полосе (как сейчас `stale`).
- **Источник не ответил** — скелетон **не дольше 8 секунд**, затем объяснение и «Ещё раз».
  Ноль и «нет данных» — разные вещи.

### 5.8 Вход — `8c-vhod-tishina.html` (вариант «Тишина»)

Главное правило: **случайный посетитель не узнаёт ничего** — ни названия панели, ни что она делает,

- В центре **маяк** — лаймовая точка с редкими расходящимися кольцами. Под ним — прозрачная кнопка
  «Войти через Steam»; при наведении у неё появляется рамка, маяк светится ярче.
- **Состояния показывает маяк, а не текст.** Под кнопкой — одна строка, без объяснений:

  | состояние | маяк | кнопка | слова |

  | обычный | лаймовая точка, редкие кольца | Войти через Steam | — |
  | приглашение | **две точки с нитью**, по нити бежит огонёк — «тебя ждут» | Войти через Steam | — (имени нет нарочно: страница ничего не говорит даже приглашённому) |
  | ждём Steam | точка вытягивается в бегущую полоску | Steam… | — |
  | нет доступа | красная, неподвижная; фонарь красный | Другой аккаунт | нет доступа |
  | доступ закрыт | красная, неподвижная | — | доступ закрыт |
  | вошёл | маяк разгорается, страница гаснет | — | — |

- Никаких «пароль не хранится», описаний и предупреждений на этой странице. Предупреждение о рисках
  (§13) владелец передаёт другу сам; внутри панели — пункт «Правила и риски» в меню пользователя.

Почему не «Ядро» и не «Холст»: оба показывают название и выглядят как витрина; владелец выбрал

## 12. Несколько пользователей

Запрос владельца: дать доступ другу, чтобы тот работал сам — свои аккаунты, свой ключ площадки,
свои закупки. Это **отдельный подпроект** серверной части; дизайн шести экранов от него не меняется,
добавляются вход, меню пользователя и экран «Пользователи» (`8-vhod-i-polzovateli.html`).

### 12.1 Решения

| Вопрос | Решение |
|---|---|
| Кто что видит | **Полностью раздельно.** Каждый видит только своё. Владелец дополнительно видит экран «Пользователи» — счётчики и нагрузку, но не чужие аккаунты, ключи и деньги |
| Как входить | **Через Steam (OpenID) + одноразовое приглашение.** Пароли панель не хранит |
| Где сервер | Домашний ПК + Tailscale на первом этапе; ничего не привязывать намертво к этой машине (§12.5) |

### 12.2 Пользователь и рабочий аккаунт — разные вещи

- **Пользователь** — человек. Входит своим Steam. Steam сообщает панели только steamid профиля —
  ни инвентаря, ни кошелька это не открывает. Это пропуск.
- **Рабочий аккаунт** — Steam, который крутит гемы и покупает. Привязывается по QR на экране
  «Аккаунты», сколько угодно (в пределах лимита пользователя). Может совпадать с профилем входа,
  может быть твинком.

### 12.3 Что своё, что общее

| Своё у каждого пользователя | Общее |
|---|---|
| рабочие аккаунты (реестр), их сессии и ключи площадки | карта матчей, `entity_matches`, `supply` — открытые данные |
| «активный аккаунт» (сейчас он один на всю панель — `reg.active`) | цена ключа Clover |
| закупка: план, корзина, робот (сейчас один `job` на всю панель) | |
| продажи, выплаты, тревоги | |
| настройки накрутки и правила, включая цель счётчика | |

Сожжённые матчи (`burned`) уже ведутся по steamid рабочего аккаунта — их делить не нужно.

### 12.4 Как работает вход

1. Владелец на экране «Пользователи» жмёт «Пригласить»: имя для списка, срок (1 / 7 / 30 дней),
   лимиты (аккаунтов, работников разом). Получает одноразовую ссылку.
2. Друг открывает ссылку → «Войти через Steam» → официальная страница Steam → возврат в панель.
3. Сервер проверяет ответ Steam (OpenID 2.0, `check_authentication`) и берёт steamid из `claimed_id`.
   Первый вход по приглашению привязывает этот steamid к пользователю; ссылка сгорает.
4. Дальше друг входит кнопкой «Войти через Steam» без ссылки. Не приглашённый steamid — отказ
   «этот Steam не приглашён». Отключённый — «доступ отключён владельцем», его работники остановлены.
5. Сессия панели — кука, как сейчас (`rig_auth`), но своя у каждого пользователя; «выйти на всех
   устройствах» сбрасывает все его сессии.

Детали OpenID (адреса, поля, проверка) сверить с документацией Steam при реализации.
Нынешние защиты `auth.ts` (Host, Origin) остаются.

Владелец при переходе: нынешний вход по токену остаётся запасным для владельца, пока его steamid
не привязан; первая настройка — владелец входит токеном и привязывает свой Steam.

### 12.5 Переносимость сервера

Чтобы можно было запустить и дома, и на Railway без переделок:

- папка данных — из переменной окружения (сейчас `TOOLS` и `RIG_DB`: база 250 МБ, реестр,
  файлы сессий, токен панели);
- порт и внешний адрес панели — из окружения (адрес нужен OpenID для возврата из Steam);
- секреты (сессии, ключи площадки) — не в репозитории и не рядом с кодом;
- на каждый работающий рабочий аккаунт сервер поднимает процесс-отправщик
  (`tools/gcwatch/index.js`, входит в сеть Steam как игровой клиент). На Railway он будет
  входить с IP дата-центра — до переезда проверить на одном аккаунте.

### 12.6 Что меняется на сервере (контур, план — отдельно)

| # | Что | Где сейчас |
|---|---|---|
| П1 | Таблица пользователей и приглашений; роль «владелец» | новое |
| П2 | Вход через Steam OpenID, сессии по пользователю | `auth.ts` (общий токен) |
| П3 | Реестр аккаунтов с владельцем; «активный аккаунт» — на пользователя | `accounts.ts` (`reg.active` общий) |

их не показывает, но это доверие, а не защита. Друга об этом нужно предупредить словами.

  автоматизации, Valve может передать ему историю; Valve может ограничить или закрыть аккаунт за
  автоматизацию и **не обязан предупреждать заранее**.

**Вывод** — `HYPOTHESIS`: отправщик автоматически, без участия человека, получает игровой прогресс
(счётчик «Games Watched») — то есть делает то, что пункт C прямо описывает. Отдельной оценки Valve
именно этого протокола в открытых источниках нет. Значит: **высокий риск нарушения**, но не «точно
заблокируют» — фактическое применение зависит от политики Valve.

**Что может случиться** (`HYPOTHESIS`):

```
риск
├─ нарушение соглашения Steam
├─ ограничение торговли/рынка или закрытие рабочего аккаунта — без предупреждения
├─ передача истории автоматизации издателю игры
└─ потеря доступа к вещам, кошельку и купленным ключам на этом аккаунте
```

**Ничего из этого не обратимо из панели.**

**Что из этого следует для панели:**

- риск несёт каждый рабочий аккаунт отдельно — не держать ценное на тех же аккаунтах, что крутят;
- деньги из кошелька не копить: чем быстрее ключи уходят на Clover, тем меньше теряется при блокировке;
- **в многопользовательском режиме (§12) риск получает и друг.** Перед приглашением владелец
  рассказывает ему об этом сам — страница входа намеренно ничего не объясняет (§5.8). Внутри панели
  этот раздел пересказан в пункте «Правила и риски» меню пользователя;
- если сервер переедет на Railway, к риску аккаунтов добавится то, что сервер с чужими сессиями
  виден из интернета (§18).

Решение работать с этим риском — за владельцем. Документ его фиксирует, а не принимает.

## 14. Инварианты

Нарушение любого — ошибка, даже если «так удобнее».

1. Пользователь A не видит и не меняет данные пользователя B. **Проверяется на сервере**, а не скрытием кнопок (§18).
2. Одна внешняя денежная операция — одна запись в журнале операций (уникальный внешний номер, §16).
3. Цель счётчика нигде не записана числом — только `settings.goal` (§3.2).
4. Секреты (сессии, ключи площадки, токены) никогда не уходят во фронт, в адрес запроса и в логи.
5. Необратимое действие (накрутка, закупка, отвязка) всегда идёт через подтверждение.
6. «Устарело» ≠ «нет данных» ≠ «оценка» ≠ «известно» (§3.3).
7. Деньги на руках ≠ стоимость того, что лежит в системе (§16).
8. Каждый работник и каждая закупка принадлежат ровно одному пользователю.
9. Каждое разрушающее действие (отвязка, отключение пользователя, отзыв приглашения, сторно) оставляет
   запись: кто, когда, что.
10. Запросы к market.dota2.net идут только через общий ограничитель на ключ (§7 С0).

## 16. Деньги: определения и журнал операций

**Определения:**

| Термин | Что значит |
|---|---|
| вложено (cost) | сумма покупок гемов, по журналу закупки |
| цена покупателя | сколько заплатил покупатель на рынке Steam |
| комиссия Steam | 5 %, минимум $0.01, считается от цены вещи, платит покупатель (`VERIFIED`, FAQ Steam) |
| комиссия игры | Dota 2 — 10 % (`VERIFIED`, там же) |
| пришло на кошелёк (seller net) | цена покупателя минус обе комиссии — **из истории рынка, не пересчётом** |
| доля продавца | производная: при 5 % + 10 % покупатель платит ≈ 1,15 цены продавца, продавец получает ≈ 87 % от цены покупателя. **Не хранится и не зашивается** — вычисляется из ставок, ставки могут измениться |
| возврат | площадка возвращает деньги за непереданный лот (`refund`, статус «трейд просрочен») — отдельная запись, уменьшает «вложено» |
| кошелёк | баланс Steam Wallet, в валюте кошелька |
| в работе (WIP) | гемы, вещи, кошелёк, ключи (в ожидании и свободные), баланс Clover — **по оценке на момент** |
| реализовано | дошло до рук: выплаты Clover |
| нереализовано | всё «в работе» по текущей оценке |

Экран Продаж показывает три итога: **вложено · реализовано · в работе (оценка, с датой)**. Одной стрелки
«вложено → выведено» мало: часть стоимости ещё лежит в Steam.

**Цена площадки для ключей** (для «Куда продать ключи»):

```
platform, price, price_type (instant | bid | listing), currency,
seller_fee, depth (сколько берут по этой цене, если известно),
payout_methods[]: { method (paypal | bank | crypto), coin, network, fee_fixed, fee_pct, fee_known },
source_type (api | page | manual), source_url, checked_at, read_ok
```

Цена типа `listing` — **не** сумма на руки: это цена, по которой придётся выставить и ждать.
`read_ok = false` — последняя проверка не удалась; значение показывается как «устарело» с временем
последней удачной проверки.
«На руки за N» считается только для `instant` и `bid` и только в пределах `depth`.

**Журнал операций** — одна таблица, записи не меняются, ошибки исправляются сторно (обратной записью):

```
id, user_id, account_id, type, source, external_id (уникален в паре с source),
happened_at, recorded_at, currency, gross, fee_steam, fee_game, net,
status, raw_ref, created_by, reconciled_at
```

- `type`: покупка гема · возврат за покупку · продажа вещи · покупка ключа · выплата Clover · сторно;
- `source`: market.dota2.net · рынок Steam · вручную;
- оценки (стоимость «в работе») — отдельно, с `valued_at`, `price`, `source`: вчерашний отчёт не меняется
  от сегодняшней цены ключа. «Продано 100 ключей 3 окт по $1.66» и «сейчас 100 ключей ≈ $1.52» — разные числа.

## 18. Безопасность нескольких пользователей

Дополняет §12.

**Изоляция — инвариант 1, проверяется тестами сервера:**

```
A: GET  /api/accounts                 → только аккаунты A
A: GET  /api/stream                   → снимки только A
A: POST /api/market/buy               → только по ключу аккаунта A
A: GET/POST что-либо с id аккаунта B  → 403
```

Основа есть: `rig/server/isolation.test.ts` проверяет разделение данных по Steam-аккаунтам.
Добавить то же на уровне пользователей.

**Приглашение — это пропуск, пока не использовано:**

- случайный токен не короче 128 бит; на сервере — только его хэш;
- срок 1 / 7 / 30 дней, одноразовость, отзыв;
- перед привязкой показать профиль Steam, который войдёт («это вы?»);
- использованное приглашение не перепривязывается никогда;
- записи: создано, принято, каким steamid, кем отозвано; ограничение попыток.

**Вход через Steam (OpenID 2.0)** — при приёме ответа проверить:

- `openid.op_endpoint` — ровно `https://steamcommunity.com/openid/login`;
- `openid.return_to` — ровно наш адрес возврата;
- `openid.claimed_id` — вида `https://steamcommunity.com/openid/id/<17 цифр>`;
- подпись — запросом `check_authentication` к Steam;
- `openid.response_nonce` — повторно не принимать;
- после входа — новая сессия; кука `HttpOnly`, `Secure` (по HTTPS), `SameSite`;
- защиты `auth.ts` (Host, Origin) остаются; OpenID их не заменяет и ими не заменяется.

**Модель угроз** — от чего защищаемся:

| Угроза | Защита |
|---|---|
| чужой в сети (особенно на Railway) | вход только через Steam по приглашению; HTTPS |
| украденная кука | `HttpOnly`, «выйти на всех устройствах», ограниченная жизнь сессии |
| утёкшее приглашение | одноразовое, короткое, хэш, отзыв, показ профиля перед привязкой |
| второй пользователь лезет в чужое | проверка владельца на каждом маршруте + тесты |
| утёкший ключ площадки | ключ только в заголовке, не в логах; «заменить ключ» в Аккаунтах |
| взломанный сервер владельца | **не защищено** — §12.7, §13 |
| дубль ответа внешнего API | уникальный `external_id` в журнале операций |

## 19. Диагностика отдельно от Журнала

**Журнал** (§5.6) — для человека: что ушло, что засчитано, что решил работник.

**Диагностика** — для починки, у владельца отдельной вкладкой или файлом лога. Событие:

```
время, пользователь, аккаунт, задача (закупка/работник), номер запроса, уровень, что, почему
```

Писать как минимум: запуск, остановку и падение работника; истёкшую или отозванную сессию; старт,
остановку, повтор и отказ по цене в закупке; ошибки Steam; отказы и «слишком часто» от market.dota2.net;
расхождения при сверке; обновление цены Clover; разрыв и восстановление потока.

**Поток `/api/stream`** нумерации событий не требует: сервер каждый раз шлёт целый снимок состояния
(`buildState()`), в том числе первым сообщением после переподключения (`index.ts`, `VERIFIED`), — потерять
событие при обрыве нечем. Свежесть уже отслеживается (40 с тишины → «данные устарели»). В диагностику
пишется только факт разрыва и восстановления.

Принцип: **`/api/stream` — транспорт состояния, а не журнал событий.** Его сообщения нельзя
переигрывать и складывать; если понадобятся события по одному — это отдельный механизм с номерами.
